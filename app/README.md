# DirectorLink app (PWA)

The DirectorLink app on **https://app.directorlink.io**. It is framework-free HTML, CSS and JavaScript and needs no build step. The API console is its own site (`../console/`, https://console.directorlink.io).

## Structure

- `index.html` — app shell: tab bar, the screen container and `theme-boot.js`
- `theme-boot.js` — blocking script in `<head>`: applies the saved palette, theme and text direction before the first paint (the CSP forbids inline scripts)
- `app.js` — entry module: hash router, renderer, dialogs, start-up
- `js/` — ES modules, no build step:
  - `state.js` (shared state + redraw scheduling), `session.js` (pairing without sending the code (CPace, `cpace.js`) and, with an older driver after a warning, with a key exchange, sealed requests on the home network with a fallback to the key for older drivers, reconnect, 10 s refresh, 401 handling, room rename, key revocation), `controls.js` (optimistic device commands, confirmation by re-reading, door/gate pulse with confirm step), `camera-feed.js` (snapshots as blobs, visible tiles only, paused while hidden; live pictures about every second), `doorbells.js` (noticing rings, Dismiss, notifications), `account.js` (sign in with Google or Apple through api.directorlink.io, only with the sign-ins it says are set up; sign out on this device or everywhere, delete the account; a device that never signed in asks nothing until someone taps Sign in), `lock.js` (the end-to-end lock in WebCrypto, checked against `tests/vectors/lock.json`), `remote.js` (sealed requests through the account and on the home network, linking a home, invitations and their links, and requests to join with another email), `platform.js` (iPhone and iPad), `qr.js` (QR codes, with the vendored MIT `vendor/qrcodegen.js`), `rings.js` (when a ring is recent, relative times; no browser dependencies, unit-tested), `setpoints.js` (thermostats with heat and cool setpoints: which ones show, the gap kept between them and the push, what counts as confirmed; no browser dependencies, unit-tested), `refrigerators.js` (Samsung refrigerators, 1.7.0: their features, what counts as confirmed and for how long, a scene action's setting; no browser dependencies, unit-tested), `reorder.js` (moving one room of the list: where a dragged room lands, the keyboard's moves, auto-scroll near the edges; no browser dependencies, unit-tested), `alarm.js` (the alarm's status, read-only: when to ask for it, every 10 s, and its words; unit-tested), `music.js` (Sonos: what each Sonos room plays, read every 5 s while Home or its room is open, play, pause, skip, volume and favorites shown at once and put back when refused, album art through the controller, an admin's room for a Sonos room; unit-tested), `find.js` (Find my controller: where to look, in which order, how many at a time and for how long; no browser dependencies, unit-tested), `turn-off.js` (Home's Turn off all: which devices, the second tap, one `POST /v1/off`), `backup.js` (backups: the file locked with a password in WebCrypto, the strength hint, the parts sent back, the check and the restore), `cloud-backup.js` (automatic backups to the account: the backup password's X25519 key pair, made here with PBKDF2, and a sealed backup opened with it; checked against `tests/vectors/cloud_backup.json`)
  - `model.js` (room names per language, grouping, "on" counts), `favorites.js` (per controller, in `localStorage`), `components.js` (device rows and tiles), `dom.js`, `icons.js` (inline stroke SVG), `theme.js`, `i18n.js`, `pwa.js` (service worker, install prompt), `calendar.js` (the Jewish calendar: whether it is on, reading `GET /v1/calendar`, Hebrew numerals and dates, holiday and weekly-reading names, the lines on Home and Schedules; see Shabbat and holidays)
  - `views/` — `home.js`, `room.js`, `cameras.js`, `climate.js`, `settings.js` (Settings' list and its pages), `connect.js` (first-time setup), `find.js` (Find my controller, under the address), `join.js` (accepting an invitation), `device-join.js` (joining from another device and Paste invitation link, ADR-053; its keys, code and seal are in `js/device-join.js`), `alarm.js` (the alarm on Home and in Settings), `music.js` (a Sonos room's card, Home's Music playing, and the Sonos rooms for the Rooms page), `backup.js` (Settings → Controller → Backup), `cloud-backup.js` (its Automatic backups to your account), `history.js` (Settings → Controller → History), `common.js` (header, connection chip, shared states)
- `i18n/en.js`, `i18n/he.js` — interface text
- `styles.css` — the app's styles
- `api-client.js` — shared client for the LAN API (API port, API key storage, pairing code format, `fetch` with Local Network Access annotations); `console/api-client.js` is an exact copy (`scripts/check_sites.py` compares them)
- `_redirects` — sends the old `/console.html` and `/console` to https://console.directorlink.io (301); Cloudflare reads it, it is not published
- `sw.js` — offline mode (see below); it never intercepts controller/LAN requests

## Screens

Hash routes, so Back and reload work: `#/` Home, `#/room/<id>`, `#/cameras`, `#/climate`, `#/settings` and its pages (`#/settings/controller`, `rooms`, `calendar`, `account`, `app`, `about`), `#/join/<invitation>` (taken out of the address as the page opens; see Remote access), `#/access` (People and devices).

## Schedules

Scenes → **Schedules** (`#/schedules`; `js/views/schedules.js`, `js/schedules.js`, `docs/SCHEDULES.md`) lists `GET /v1/schedules`, each in a sentence with its next or last run, and the weather at home from `GET /v1/weather` (read while the screen is open; the controller then keeps it fresh). Admins switch schedules on and off (`PATCH` `enabled`) and edit them at `#/schedule/new` and `#/schedule/{id}`: the scene, when (a time, sunrise/sunset with an offset, or heat/rain/wind with hours and at most once a day; with the Jewish calendar on, also Shabbat: see below), the days, and "only if" weather conditions. Drivers older than 0.14.0 answer 404: the screen says to update the driver.

## Shabbat and holidays

Shabbat and holiday times, the Hebrew date and the week's reading, worked out on the controller (`GET /v1/calendar`, ADR-037; `js/calendar.js`). All of it shows only while `GET /v1/system` says `features.jewish_calendar: true`, which is DirectorLink's **Jewish Calendar** property in Composer (Off by default). A driver before 1.2.0 has no `features`: the app then shows none of it, never asks `/v1/calendar` and never sends `during_shabbat` (such a driver refuses fields it does not know). A `409 JEWISH_CALENDAR_OFF` answer (the property was turned off since `/v1/system` was read) turns it off in the app too until the next read, and says why.

- **Reading** — after connecting, then with the rooms refresh every 10 minutes while the app is in front, on entering Home or Schedules, after saving the settings, and 5 seconds after the next moment the answer changes: the current period's end, the next one's start or end, or today's sunset (from the weather when Schedules has read it, and on the eve of a period from its candle lighting). The answer is `state.calendar`.
- **Home** — under the notices, today's Hebrew date (the next day's from sunset, as the API gives it), its holidays and the week's reading: *18 Tishrei 5787 · Chol HaMoed Sukkot · Shabbat Shmini Atzeret*, *י״ח בתשרי תשפ״ז · חול המועד סוכות · שבת שמיני עצרת*, *24 Tishrei 5787 · Parashat Bereshit*.
- **Schedules** — under the weather, for everyone: the next Shabbat or holiday (its days' names in order: "Shabbat" for a Saturday, then its holy days) with its candle lighting and havdalah, or the one now with its havdalah and the candle lightings still to come in it; "No sunset at this latitude" in polar summer and winter; without a location, where to set it. A footnote gives the minutes and Israel or abroad; admins get **Change**, which opens Settings → Shabbat and holidays.
- **The editor** — a fourth kind of When, **Shabbat**: candle lighting or havdalah (with the next times), and when: from 2 h before to 2 h after (an offset set otherwise through the API, up to 6 h, shows as one more chip). Holy days that follow each other are one period, so it runs once when the period begins or ends; its days are not shown (a new one gets all seven, one made through the API keeps its own). Time, sun and weather schedules get **On Shabbat and holidays**: Run as usual, Not on Shabbat and holidays, or Only on Shabbat and holidays (from candle lighting to havdalah), sent as `during_shabbat` (`run` for a Shabbat trigger, which clears the condition it had). With the calendar off, a Shabbat schedule's editor offers only its switch and Delete, and a condition set earlier is kept and explained.
- **The list** — "30 min before candle lighting", "At havdalah", "Only on Shabbat and holidays"; "Didn’t run today 06:30: Shabbat or a holiday", "Ran today 09:10 (late, after a restart)"; and, by `calendar_status`, "Not running: the Jewish calendar is off in Composer" (or: set the home's location) for Shabbat triggers and "only" schedules, while "not on Shabbat" ones say they run on Shabbat too meanwhile.
- **Settings → Shabbat and holidays** (admins) — Automatic (it says what the home's location gave), As in Israel (one day of Yom Tov) or Abroad (two); candle lighting 0–90 minutes before sunset (18, 20, 30, 40) and havdalah 20–90 after (42, 50, 72). Save sends `PATCH /v1/calendar/settings` with the `version` read; a `409 VERSION_CONFLICT` shows the settings as they are now, to change again.
- **Names** — the API sends only keys and numbers (`HebrewMonth`, `HolidayKey`, parasha ids 1–54); `calendar.months`, `calendar.holidays` and `calendar.parashot` in each dictionary hold the names, and `scripts/check_app.py` fails when one of the API's keys has none. English follows Hebcal's spelling; Hebrew too, except the full spellings מצורע, קדושים, בחוקותי and בהעלותך. Two readings read together are joined with `-` in English and a maqaf (־) in Hebrew (`calendar.join`). Hebrew writes days and years in Hebrew letters (`calendar.numerals`: ט״ו, ט״ז, תשפ״ז, the year without its thousands). `tests/app/calendar.test.mjs` covers the numerals, dates, names, the texts, what the editor offers and sends, the lines for the API's examples (`tests/vectors/calendar/api-examples.json`) and when the calendar is read.

## Scenes

The **Scenes** tab (`js/views/scenes.js`, `js/scenes.js`, `docs/SCENES.md`) lists the home's scenes from `GET /v1/scenes` with a Run button (`POST /v1/scenes/{id}/run`, members and above). Admins make and change them in the editor (`#/scene/new`, `#/scene/{id}`): name and icon, the actions (Add an action at `#/scene/{id}/add`: where, what, which devices, what to do; since 1.6.0 an action's Edit button, or its text, opens the same screen filled in from it at `#/scene/{id}/edit/{index}`, and Save action puts it back in its place), **Copy the house as it is now**, **Show on Home**, **Try it now** (`POST /v1/scenes/try`) and Save (`POST`/`PATCH /v1/scenes`, with `version`). Scenes marked Show on Home are on Home, above the favorites. Drivers older than 0.13.0 answer 404: the tab says to update the driver.

## Turn off all

On Home, a list a summary chip filters (lights on, AC on, blinds open) has a button next to **Show all** for members, doors and admins (`js/turn-off.js`; never on the chip itself, and viewers do not get it): *Turn off all 7* (lights), *Turn off all 3* (climate: AC, floor heating and thermostats that are not Off; one without an Off mode is left out), *Close all 4* (blinds that are open and not already closing); with one, *Turn off the light*, *Turn off the AC*, *Close the blind*. It acts on the ones on or open in the rooms the list shows at that moment: rooms you hide stay as they are.

- **Second tap** — the first tap makes it *Tap again to turn off 7* (*Tap again to close 4*), with Cancel in place of Show all, for 5 seconds, as a door's Open button does. There is no undo.
- **One request** — the second tap sends `POST /v1/off` with `type` and `device_ids` (members; 1.3.0): lights off, thermostats to Off (as a scene's All AC: Off), blinds to 0. A driver before 1.3.0 answers 404; each device then gets its own `PATCH`, all at once.
- **Results** — *Turning off…* (*Closing…*), then *Done* for a few seconds. Lights and AC show off at once, blinds show *Closing…* and are read every 2 s until they stop, and the devices are read again 1.5 s later, so the chips' counts follow. Devices that did not turn off are named with their room for 15 s (the first 8, the rest counted), and the button is there again for them; a request that failed says why and changes nothing.
- The button goes when nothing in the list is on or open any more; the filter stays. `tests/app/turn-off.test.mjs` covers the count and words, the second tap, its 5 seconds and Cancel, viewers, which devices are named, partial failures and the requests.

## Profiles

Each person's language, theme, palette, favorites and hidden rooms are kept on the controller, in their profile, and shared by their devices (`js/profile.js`, `docs/PREFERENCES.md`). After connecting, and every minute, the app reads `GET /v1/profile` and applies it; the first time, this browser's own choices become the profile's; changes go back with `PATCH /v1/profile` a moment later. The browser keeps a copy, so the app opens in the right language before it reaches the controller and works as before with drivers older than 0.12.0. Settings → Rooms: untick a room to hide it for yourself; admins set the home's order by dragging a room by its handle (on a touch screen, held first; a swipe that starts on it still scrolls), with the keyboard (Space or Enter picks it up, the arrow keys, Home and End move it, Space or Enter puts it down, Escape puts it back; the place is read out), or one place at a time with the arrows. Each move is one `PUT /v1/rooms/order`; moves made while one is on its way go together in the next, and a refusal puts the order back. **Add my other device** makes the new device join your profile.

- **Home** — a doorbell banner while someone rings (see Doorbells), connection chip, the Hebrew date and the week's reading (with the Jewish calendar on; see Shabbat and holidays), the alarm (see Alarm), summary chips ("2 lights on", "1 AC on", "1 blind open"; tapping one filters the rooms, and the filtered list has **Turn off all**: see below), Favorites (Edit mode to add, remove and reorder), room cards. Without a key it shows the connect screen: controller address and **pairing code** (see below).
- **Room** — All off (lights and AC), then Lights, Climate, Blinds, Refrigerators (drivers with `/v1/refrigerators`, 1.7.0: the fridge's and freezer's temperatures, the door, the water filter, and a switch per feature that says "Turning on…" until the refrigerator confirms through Samsung's cloud, read every 2 s for up to 65 s, then quietly every 5 s for 2 minutes more, so that a late confirmation still shows), Doorbells (drivers with `/v1/doorbells`), Doors & gates (drivers with `/v1/relays`), Cameras (without the doorbell's own camera, shown with the doorbell) and the room's other, uncontrollable devices. Empty sections are hidden; the star on each device adds it to Favorites.
- **Cameras** — one large picture and a grid; thumbnails refresh about every 3 s, the full view about every second.
- **Climate** — all thermostats grouped by room. A thermostat with heat and cool setpoints (`setpoints: dual`, drivers from 1.1.0) has a Heat or a Cool stepper in heat and cool, and both in auto and off (stacked on phones); raising heat into the gap moves cool up and lowering cool moves heat down, and the taps go out as one `PATCH` with `heat_setpoint` and `cool_setpoint`.
- **Settings** — appearance and language, then a row for each page, with a line saying how things are ("2 rooms, 1 hidden", "Connected · Up to date"; a badge on Controller when a newer DirectorLink is out): **Controller** (`#/settings/controller`: address, status, the project; admins: History, see below; Updates with the app's and DirectorLink's versions, Check now and how to update; admins: Backup, see below; Pair again, Forget access key), **Rooms** (`#/settings/rooms`: which rooms you see; admins: the home's order and the names per language, `PATCH /v1/rooms/{id}`; then the Sonos rooms, admins with Sonos on: see Music), **Shabbat and holidays** (`#/settings/calendar`, admins, with the Jewish calendar on), **People and devices** (`#/access`, admins), **Account** (`#/settings/account`: sign in with Google or Apple, which comes back here, sign out, add or remove a sign-in, delete account, and This home: link it, Add my other device, Invite someone; `docs/ACCOUNTS.md`), **App** (offline copy, install, API console — opens https://console.directorlink.io, or `http://127.0.0.1:8081` when the app runs on localhost; doorbell notifications) and **About**. Each page has Back to the list, which then focuses the row that opened it. The controller's project counts include doorbells.

## Alarm

Read-only (docs/DECISIONS.md, ADR-038). Only when `GET /v1/system` says `features.alarm_status` (an installer set **Alarm Status** to On in Composer) and only for member, doors and admin keys does the app ask `GET /v1/alarm` (sealed, like every request), after connecting and every 10 s. Home then shows each partition the alarm uses — its name and room, and "Armed away", "Disarmed, not ready", "Entry delay", "Alarm: fire"… with open zones, the seconds a delay has left (counted down between reads) and trouble — and Settings → Controller has an Alarm line. There is nothing to press: the app never arms or disarms. With Alarm Status off, and for viewers, nothing is asked or shown; a refusal (`403`, e.g. a request that could not be sealed) or an older driver (`404`) shows nothing; without an answer the last status stays while Home says the controller cannot be reached.

## Music (Sonos)

Only when `GET /v1/system` says `features.sonos` (an installer set **Sonos** to On in Composer; docs/SONOS.md, ADR-044). After connecting the app reads `GET /v1/music` once, then every 5 s while Home (all rooms) or a room (`?room_id=`) is open, and not on other screens. A room's screen has a Music card for each Sonos room shown there: album art (`GET /v1/music/{id}/art`, as a blob like camera pictures), what plays, its state and group; members and admins get previous, play or pause and next (left to right in Hebrew too, as media controls are), the volume and mute, and the Sonos favorites, which load when opened and, after an error, with Retry (those only the Sonos app starts are greyed out). Home lists each group that plays, with a pause button. A Sonos room whose name matches no room is under No room until an admin picks its room (`musicRoomsSection()` in `js/views/music.js`, on Settings → Rooms); the first choice, "Same name: Kitchen" or "Not in a room", puts it back to matching by name. A command shows at once on every room of the group and is put back, with a short error, when the speaker refuses it. Scenes have a Music action (pause or stop, in a room or the whole home).

## Backup

Settings → Controller → **Backup**, for admins (`js/backup.js`, `js/views/backup.js`, `docs/BACKUP.md`, ADR-042). **Download backup** asks for a password twice (10 characters at least, with a strength hint, and says that without it the file cannot be opened), reads `GET /v1/backup`, locks it here with WebCrypto (PBKDF2-SHA-256, 600,000 iterations, a random salt; AES-256-GCM, a random IV, the header authenticated) and saves "DirectorLink backup <home> <date>.dlbackup". **Restore from backup** takes the file and its password, opens it here (a wrong password, or a changed file, opens nothing and sends nothing), sends it in parts (`POST /v1/restore/parts`, each under 30 KB of JSON so that it fits a sealed request) and shows the controller's check (`POST /v1/restore`): first, when the backup looks like another home's, a warning naming it and why; the date and version, the counts, the keys that come back by name and role (or that the keys are kept as they are now), devices found by name, what is not in the project and where it was used, what is left out, remote access, and the Composer settings to set by hand. Where the backup's keys come back, **This device is** lets the admin pick the key this device had before (`replaces_key`); for another home's backup, **Move remote access to this controller** (`move_remote`) is off unless ticked. **Replace everything**, confirmed with the home's name, restores it (`"dry_run": false`; an upload the controller no longer has is sent again), then the app reads everything again, and a device linked through the account to another home is pointed at the backup's. The password never leaves the browser, and is never written into the page's HTML; the opened document goes only to this controller, in sealed requests. The passwords, the file and the opened backup stay in `js/views/backup.js` (never in storage or `ui`) and go when the panel closes or the key is forgotten. A file over 4 MB is not read. The panel shows only when `GET /v1/system` says `features.backup` (a DirectorLink from 1.4.0; an older one has no backups); a `404` from the controller says to update DirectorLink in Composer. `tests/app/backup.test.mjs` covers the file, the parts and the panel. The preview counts the Sonos rooms when the backup has them (1.6.0).

**Automatic backups to your account** (1.6.0, ADR-048; `js/cloud-backup.js`, `js/views/cloud-backup.js`), in the same card, for admins signed in to their account, with a DirectorLink that says `features.automatic_backup`. **Set backup password** asks for it twice, with the same strength hint, says plainly that without it the backups cannot be opened, makes an X25519 key pair from it here (PBKDF2-SHA-256, 600,000 iterations, a random salt) and sends the controller only the public key, the salt and the iterations (`PUT /v1/backup/automatic`, sealed); then it backs up at once (`POST /v1/backup/automatic/run`) and asks the controller every 3 s until that is done. The card says when the nightly backup runs (the controller's time) and how the last one went, with **Back up now**, **Change backup password** (backups made before keep their old password; the list marks them "earlier password") and **Turn off** (the account's backups stay). Below, the backups in the account (`GET /v1/homes/{home_id}/backups` for each of the account's homes it may see, this device's linked home first): date and size, **Restore…** and **Delete these backups**. Restore asks for the backup password, downloads the backup, opens it here (a wrong password opens nothing and sends nothing) and hands the document to the same check, preview and Replace everything as a file. The passwords stay in `js/views/cloud-backup.js`, never in storage or `ui`. `tests/app/cloud-backup.test.mjs` covers the key, the shared vectors and the section.

## History

Settings → Controller → **History**, for admins (`#/settings/history`; `js/views/history.js`, `docs/HISTORY.md`, ADR-046). It reads `GET /v1/activity` 50 entries at a time (**Load more** asks `before` the last one shown), newest first, a section a day in the home's time zone (Today, Yesterday, then the date): an icon per kind, what happened and who in one line (a key's device and its person, a schedule as Schedules says it, Composer or DirectorLink), the time, and how it went (what ran, what was skipped and why in plain words, what failed). Names from Control4 keep their own direction. The chips (a group of toggle buttons) show All, Scenes and schedules, Doors, Changes in Composer or Access. While open, the newest are read again every 30 s and go on top; a screen reader hears how many entries are shown. Alert notifications open `#/settings/history`; for a key that is not an admin's it shows Settings' list. A DirectorLink before 1.6.0 answers `404`: the page says to update it. Back leads to Settings → Controller with its History link focused. `tests/app/history.test.mjs` covers the link, the page, the chips, Load more and Hebrew.

## Pairing

The pairing code is the only way to get a device's first key. In Composer: DirectorLink → Actions → **New Pairing Code** (one is also made when the driver is added or has no keys); Composer shows it as `1234 5678`. A code lasts 15 minutes and works once. The field brings up the number pad (`inputmode="numeric"`, `autocomplete="one-time-code"`) and formats the code as it is typed or pasted, with or without the space or a dash. The code is never sent: the app pairs with CPace (`js/cpace.js`, docs/DECISIONS.md, ADR-039), two requests to `POST /v1/auth/pair` that give an admin key sealed for this exchange; the name is the browser and system, e.g. "Chrome on Windows". A driver before 1.3.0 refuses the field `cpace`: the connect screen then warns that the code would travel over the network unprotected and that DirectorLink should be updated in Composer, and only **Pair anyway** sends `{"pairing_code", "name", "exchange"}` (`pairSealed` in `session.js`: sealed for this device's X25519 key exchange; browsers without X25519, and drivers before 1.0.0, pair without `exchange` and get the key in the clear). Every problem it can answer has its own message in each language: `INVALID_FIELD` (not 8 digits), `PAIRING_CODE_INVALID` (with the tries left), `PAIRING_NOT_ACTIVE` (no code — run New Pairing Code), `PAIRING_RATE_LIMITED` (5 wrong codes lock pairing for this device for 60 s; 20 in all close the code, then `PAIRING_NOT_ACTIVE`), `KEY_LIMIT_REACHED`, `PAIRING_UNAVAILABLE`, `PAIRING_SESSION_EXPIRED` (the exchange took over a minute), `PAIRING_CODE_EXPIRED` (a new code was made meanwhile), and a controller that could not prove it knows the code. More keys, with other roles, are created by an admin in the API console (Keys).

### Find my controller

Under the address field (`js/find.js`, `js/views/find.js`). A web page cannot learn this device's address or network, and browsers cannot look for devices by name (mDNS, SSDP), so the app asks `GET /v1/health` on port 41999, which needs no key, at the addresses homes use most. It sends nothing else: no key, no pairing code, and each request is sent as `api-client.js` sends them (`targetAddressSpace: "local"`, see Local Network Access).

- **Where** — first the address this browser used before, if any, and the routers' usual addresses (x.1, x.254 and x.138, Bezeq's) of each network: a network whose router answers, even to refuse, is looked through first. Then, in this order: the used address's network, 192.168.1.x, 192.168.0.x, 10.0.0.x (Bezeq), 10.0.1.x, 192.168.2.x, 192.168.10.x, 192.168.50.x, 10.1.1.x, 172.16.0.x, each from .1 to .254.
- **How** — at most 64 requests at a time; an address that does not answer within 1.2 s is given up (a router within 2 s). The whole search takes 30 seconds at most: a request that could not end within them is not started, so the last networks may not be reached. The line under the button says what it is doing ("Looking in 192.168.1.x…"); the button becomes Cancel, which drops every request on its way.
- **Recognising it** — the health answer's `product: "directorlink"` (drivers from 1.3.0); older drivers by their answer's fields (`status`, `version`, `api_version: "1"`, `detail`). The browser reads an answer only when the device allows the app's origin (CORS), so other devices on port 41999 go unread.
- **Found** — its network is looked through to the end, then the search stops. One: it goes into the address field ("Found DirectorLink 1.3.0 at 192.168.1.50") and the pairing code field comes next; an address typed meanwhile is not replaced. Several: they are listed with their versions to pick from. The person still types the code and taps Connect.
- **Not found** — "No controller found on this network. Type the controller's address. Your installer can tell you, or find it in Composer."
- **The browser's question** — while Chromium asks whether the site may reach the local network, every request waits: the first ones are sent once, the search waits up to 30 s for the answer ("Allow access to devices on your local network when the browser asks"), then starts. Refused: it says how to allow it in the site's settings.
- **Where it is offered** — only where pairing at home works: Chromium browsers on computers and Android (`findSupported`). Not on iPhone and iPad, whose pairing screen sends people through the account, nor in Firefox or Safari.

`tests/app/find-controller.test.mjs` covers the order, the routers first, 64 at a time, the timeouts, the 30 s, Cancel, one, several or no controllers, the browser's question, what is sent and the browsers it is offered in. To try it with the dev server (Local development), make it look on this computer from the browser's console, then tap Find my controller: it finds 127.0.0.1.

```js
(await import("/js/find.js")).scanSettings.ranges = ["127.0.0"];
```

API key roles (drivers from v0.7.0): on connect the app reads `GET /v1/api-keys/current` (404 on older drivers → treated as admin) and shows only what the key may do — `viewer` sees state without controls, `member` controls lights, climate and blinds, `doors` also opens doors and gates (after a confirming second tap), `admin` also renames and orders rooms, makes scenes and schedules, and manages People and devices and invitations. A 403 `FORBIDDEN` reverts the change, shows "Your access level (…) can't do this" and adopts the role it reports; `DOOR_CONTROL_DISABLED` explains how to turn Door Control on in Composer. Forget key and Pair again revoke the key with `DELETE /v1/api-keys/current` (older drivers: the key list); a 401 on any request forgets the key and asks for a new pairing code.

## Doorbells

DoorBird doorstations come from `GET /v1/doorbells`, polled with the other devices every 10 s (an older driver answers 404: no doorbells; other failures keep the last list).

- **Ringing** — a ring is recent for 2 minutes: when its `last_ring_at` is within 2 minutes of this browser's clock (a controller clock up to 2 minutes ahead is believed), or when this page saw `last_ring_at` change within the last 2 minutes, whatever the clocks say. While it is recent, Home starts with a banner — "Someone is at the door — <name>", the doorbell's camera refreshed about every second, **Open gate** and **Dismiss** — and the other screens show one line that leads to it. Dismiss remembers that `last_ring_at` (per controller, in `localStorage`); the next ring shows the banner again.
- **Open gate** — doors and admin keys, on doorbells with `can_open`: a second tap within 5 s sends `POST /v1/doorbells/{id}/open` (Opening… → Sent). `403 DOOR_CONTROL_DISABLED` explains the Composer switch.
- **Room** — the picture (tap for the full view), "Last ring: 3 minutes ago · Motion: …", "Not responding" after a communication failure, the last five events with relative times (`Intl.RelativeTimeFormat`), and Open gate.
- **Favorites** — a starred doorbell shows its last ring and opens its room; it is highlighted while ringing.
- **Notifications** — Settings → App → **Turn on doorbell notifications** asks for the permission (so does Alerts, below). A ring then notifies (through the service worker when there is one) while the app is open but not in front; in the background only `/v1/doorbells` is polled. With the app closed, a ring comes as an alert (below, DirectorLink 1.7.0), under the same tag (`doorbell-<id>`) with the ring's time: a ring one of them shows already is not shown twice. Clicking the notification brings the app to Home.

Controls change the screen at once, send the command, then re-read the device until the controller confirms it; a failed command reverts and shows a short error on the device. Device state refreshes every 10 s while the page is visible.

## Alerts

Notifications with the app closed (Web Push; 1.6.0, ADR-047; 1.7.0, ADR-050): someone rang at a door ("Front gate rang at 08:00."), a door or gate was opened ("Main door was opened by Dana (Dana's iPhone) at 08:01."; admins, if they choose), the refrigerator door was left open, a schedule had a problem (admins), the home has been offline for 10 minutes (admins). The controller decides who gets what (each key's role and its own choices) and seals what happened to each device's key; the account service only delivers it. Tapping a ring opens Home, a refrigerator's alert its room, the others Settings → Controller → History (`#/settings/history`). With a controller before 1.7.0 (no `features.alert_choices`), as in 1.6.0: admins only, the offline and schedule alerts, which say only their kind and time.

- **The switch** — Settings → Controller → **Alerts on this device** (`js/views/alerts.js`), for everyone signed in to an account on a device linked to the home (else it says to link it); admins only with a controller before 1.7.0. Once on, a switch per kind the controller offers this key (`GET` and `PUT /v1/alerts/choices`, sealed), and for admins the offline alert, which the account service keeps (`offline` in the registration). Turned on, it asks for the permission (the only other place that does is doorbell notifications), subscribes the browser with the account service's public key (`GET /v1/homes/{home_id}/alerts`, `pushManager.subscribe` with `userVisibleOnly`), registers it with this device's key id (`POST`, `key_id`) and tells the controller (`PUT /v1/alerts/choices` `{"on": true}`; a controller that cannot be told leaves alerts off). Off unregisters it (`DELETE`), drops the subscription and tells the controller. The account service refuses an account that has not used this device's key at the home yet (`KEY_NOT_LINKED`: the app first tells it with one sealed request through the account, then asks again; when that request does not reach the home, it says the home could not be reached). Signing out, Sign out everywhere, deleting the account and forgetting the key end this browser's alerts too.
- **iPhone and iPad** — only the app added to the Home Screen gets them, on iOS 16.4 or later. In Safari the card says how (Share → Add to Home Screen); added on an older iOS, which version it needs.
- **Each start** — signed in, the app registers again (`js/alerts.js`): the browser may have a new subscription, the account service a new key (the app then subscribes again), or the device may no longer be allowed (the switch turns off and says why). A controller that does not know this device has alerts on (switched on by an app before 1.7.0, or restored) is told.
- **The words** — the service worker (`sw.js`, `push`) opens what the controller sealed to this device with its alert key, `HMAC-SHA256(lock key, "DirectorLink alert v1")`, which `js/alerts.js` keeps for it in Cache Storage (`directorlink-alerts`, `/alert-key.json`, with the home and key id; never the lock key or the API key), checking the MAC first (`tests/vectors/alert.json`). It writes the sentence with the app's own words in the app's language, kept there too and written again when the language changes; the time is this device's. The account service's offline alert, and anything that does not open, get the general words (“Your home – …”). Without the app's words, English. Every push shows a notification: a ring the app already shows, or shows on its banner because it is in front, is shown again quietly in its place.

## Updates

For admin keys, the app says when a newer DirectorLink is out (`js/updates.js`, `js/views/updates.js`, ADR-035). At most every 12 hours it asks GitHub's releases API (`https://api.github.com/repos/IsraelCIL/DirectorLink/releases/latest`, without cookies; the CSP's `connect-src https:` allows it) and keeps the answer in `localStorage`. Settings → Controller shows **Updates**: *Up to date*, or the newer version and its date with **Download DirectorLink.c4z** (that release's file), **What's new** (the release page, in a new tab) and the steps in Composer; Home shows a notice until it is dismissed for that version. Other roles never ask, nor does a driver whose version is not MAJOR.MINOR.PATCH (`dev`); a failed request keeps the last answer and its time until the next try. *Up to date* is said only within 3 days of GitHub's last answer, then *Could not check for updates* with that day; a newer release already known stays offered. Only immutable releases are offered (their files cannot be replaced), and only the version, the date and links into the project's releases are used, never the text of the release notes. The rooms refresh, once a minute, reads `GET /v1/system` again, so after Update Driver in Composer the line says *Up to date* without a reload. `tests/app/updates.test.mjs` covers the comparison, the 12 hours, the 3 days, the admin-only rule and the answers that are refused; `tests/app/update-notice.test.mjs` the screens and the refresh. **Check now** (1.5.0), under Settings → Controller, asks GitHub at once, at most once a minute, and the 12 hours start again from it; Settings also shows the app's own version (`js/version.js`, kept equal to the release's VERSION by `scripts/check_app.py`).

## Palettes and themes

Five palettes — graphite (default), ocean, forest, plum, midnight — each with a light and a dark variant, as CSS custom properties on `:root[data-palette=…][data-theme=…]` in `styles.css` (tokens `--bg`, `--card`, `--nav`, `--ink`, `--muted`, `--line`, `--onBg`/`--onText`, `--coolBg`/`--coolText`, `--primary`/`--primaryText`, `--okBg`/`--okText`/`--okDot`). The theme is Light, Dark or Auto (follows `prefers-color-scheme`); `data-theme` always holds the resolved value. The choice is stored in `localStorage` (`directorlink.palette`, `directorlink.theme`) and `meta[name=theme-color]` follows the page background. Adding a palette: a light and a dark token block and a swatch rule in `styles.css`, its name in `PALETTES` (`js/theme.js`) and `theme-boot.js`, and a label under `palettes` in each language file.

Fonts are Sora (headings) and IBM Plex Sans / IBM Plex Sans Hebrew (text) from Google Fonts, with system fallbacks — the offline copy renders without them.

## Languages

Every string on screen goes through `t(key, params)` from `js/i18n.js`, with plural forms chosen by `Intl.PluralRules` (`{ one: …, two: …, other: … }`). Language is Auto (browser languages), English or עברית, stored as `directorlink.lang`. Hebrew sets `<html lang="he" dir="rtl">`; the layout uses logical CSS properties, so it mirrors, and directional icons flip. Names from Control4 are rendered with `dir="auto"`. Rooms show `room.names[lang]` when set in Settings → Rooms, else the Control4 name.

To add a language:

1. Copy `i18n/en.js` to `i18n/<code>.js` and translate the values (missing keys fall back to English).
2. Add one line to `LANGUAGES` in `js/i18n.js`: `{ code: "<code>", label: "<name in that language>", dir: "ltr" | "rtl" }`.

Optionally list the file in `ASSETS` in `sw.js` so it is saved for offline use at install; otherwise it is saved the first time it is used. For a right-to-left language, also add it to the direction check in `theme-boot.js` to avoid a flash of the left-to-right layout.

## Offline mode

The service worker saves the app on the device, so it still opens when the internet is down and keeps controlling the house over the LAN:

- every same-origin `GET` goes to the network first and falls back to the saved copy when the network fails or takes longer than 3 seconds; each successful load refreshes the saved copy, so it never goes stale
- pages are saved under every path that serves them — Cloudflare redirects `/index.html` → `/` — and stored without the redirect, because browsers refuse redirected responses for page loads; redirects to other sites (the old console addresses) are left to the browser and never saved
- controller requests are cross-origin and are never intercepted or cached
- Settings → App → **Offline copy** shows whether the app is saved

`tests/app/sw.test.mjs` checks this against a fake network that serves the app the way Cloudflare does. Tests live outside `app/` because Cloudflare publishes everything in this folder.

## Cloudflare

The app is the Cloudflare Workers static-assets project `directorlink-app` on the `app.directorlink.io` custom domain ([`wrangler.jsonc`](wrangler.jsonc): assets from `.`, Cloudflare's default HTML and 404 handling). `.github/workflows/deploy.yml` runs `wrangler deploy` from this folder on pushes to `main`; pull requests get preview versions (the `previews` block).

`_headers` sets the security headers, `_redirects` the old console addresses; `.assetsignore` keeps `wrangler.jsonc`, `.assetsignore` and this README from being published. No environment variables are required. Every merge to `main` deploys, so web changes must go out together with the driver version they need.

## Local development

The driver answers browsers only from `https://app.directorlink.io` and `https://console.directorlink.io` (since 1.0.0, not `localhost`), so a local copy of the app talks to the fake controller of the dev server, which allows local origins:

```bash
python scripts/dev_server.py                  # fake controller on http://localhost:41999
python -m http.server 8080 --directory app    # app on http://localhost:8080
```

Then open `http://localhost:8080`, use `localhost` as the controller address and the pairing code the dev server prints (see `docs/BUILD.md`). App changes reach a real controller once they are deployed.

## Local Network Access

The production site is served over HTTPS and talks to the controller over plain HTTP on the LAN. Chromium browsers gate these requests behind Local Network Access permission; requests to private IP literals or `.local` hostnames, annotated with `targetAddressSpace: "local"`, are allowed after the user grants it. A controller on this computer (`localhost`, the dev server) is annotated `"loopback"` instead, because Chromium blocks a request whose annotation does not match the address.

**iPhone and iPad cannot use the LAN connection.** Every browser on iOS and iPadOS uses WebKit, which blocks these HTTP requests from an HTTPS page as mixed content and has no Local Network Access permission to allow them; the request never leaves the device (the controller logs nothing) and the app shows "Could not reach DirectorLink". Pairing therefore has to happen on a computer or an Android phone. iPhones and iPads connect through the account instead (Remote access, below). The app added to the Home Screen has its own storage and never receives links (iOS opens them in Safari): it joins with **Join from another device**, or with **Paste invitation link** (1.7.0, below).

## Remote access

With an account (`docs/ACCOUNTS.md`), requests are sealed on the device with its lock key (`js/lock.js`) and sent to `api.directorlink.io`, which passes them to the home without being able to read them. On the home network the same sealed envelopes go to the controller itself (`POST /v1/sealed`), with or without an account.

- **Link this home** (Settings → Account, on the home network, admin key, Remote Access On in Composer): the app asks the controller for a claim token and gives it to the account. A home already linked to this account is only linked for this device; one linked to another account is taken over only after a confirmation.
- **Add my other device** / **Invite someone**: the controller makes an invitation (10 minutes, or 7 days for an email) and registers its id, email and expiry with the account over its own connection (drivers before 1.0.0: the app registers it, for the home's owner only), and the app shows the link and a QR code: `https://app.directorlink.io/#/join/<home>.<invitation>.<secret>`. The secret never reaches a server.
- **Joining** (`#/join`): sign in with the invited email and accept; the controller's new key comes back sealed. It replaces a key the device already had, after a confirmation. Signed in with another email (Apple's Hide My Email, another account), the page asks the home's owner and shows a 6-digit code to read out to them; it asks every 5 seconds and finishes by itself once they approve (ADR-041). A refusal or the invitation's expiry is said; the request can be withdrawn.
- **Join from another device** (1.7.0, ADR-053; `js/views/device-join.js`, `js/device-join.js`): on the Connect screen, signed in, a device without a key asks to join one of the account's homes (`POST /v1/homes/{home}/device-requests` with its label, e.g. *Home Screen app on iPhone*, and a commitment, the SHA-256 of its X25519 public key). A device of the same account linked to the home with an admin key (its role read from the controller first) looks for requests every 60 s while it is shown, at once when it comes to the front or connects, and every 2 s only while it answers one, and shows them under the header of every screen. **Show code** sends its own public key; the new device then shows its key (checked against the commitment) and its 6-digit code from the request and both keys, which the person types on the approving device (it works the code out too and never shows it). **Approve** with the same code makes the invitation of Add my other device at the controller and seals it to the new device (X25519, HKDF-SHA-256, AES-256-GCM); a wrong code approves nothing, and the third declines the request. If Approve's answer is lost, the request is read before the invitation is revoked (kept when the cloud took it). The new device collects it once, opens it and joins as with the link. **Decline** ends it. A key saved on the new device another way (pairing, an invitation's link) withdraws its request when it connects. The new device keeps its request (and its key pair's secret, for 10 minutes at most) in `localStorage` so a reload carries on, and gives up if the approving key changes after it showed its own. Offered only when `GET /v1/me` says `device_requests: true` (account service 1.7.0); errors say what to do (no device that could approve, too many requests, declined or ran out).
- **Paste invitation link** (the Connect screen; Settings → Account): reads the clipboard (`navigator.clipboard.readText`; iOS shows its Paste button) and, when that is refused, missing or holds no link, shows a field. A whole link, a message with one in it, or only the part after `#/join/`; it then opens the join page as the link would.
- **Choosing the connection**: the home network first; when it gives no answer, the account (reads are sent again that way, commands are not, so a gate never opens twice). Away from home the app checks once a minute whether the home network is back, with `GET /v1/sealed`, which needs no key (`GET /v1/remote` for drivers before 1.0.0), and returns only when the controller there is this home. iPhone and iPad always use the account. The chip says **Connected · via account**.
- Failures of the account connection (signed out, home offline) never forget the device's key; signed out, the banner offers to sign in again.
- **People and devices** (`#/access`, a row on Settings' list, admin keys): every API key with its role (changeable), when it was last used, when it expires ("expires in …", the API console's key, ADR-040), and Revoke; the invitations waiting, with Revoke; for the home's owner, the accounts that belong to the home with their devices, and Remove (their keys are revoked at home first, then the membership ends), and the accounts *Asking to join* with an invitation sent to another email: name, email or *hidden by Apple*, sign-in, the account's age, when it asked, the invitation and the code, with Approve and Refuse (`GET`/`POST /v1/homes/{home}/join-requests`). Devices and invitations come from the controller, people from the account service (`GET /v1/homes/{home}/members`). Each device shows the person (profile) it belongs to; an admin can move it to another person or rename one.

The CSP in `_headers` allows Google Fonts (`fonts.googleapis.com`, `fonts.gstatic.com`) and `blob:` images (camera pictures are fetched with the API key and shown as blobs).
