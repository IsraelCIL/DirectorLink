# Architecture Decision Record

This file records decisions that should not be silently changed.

## ADR-001 — Director OS baseline

**Decision:** Minimum supported version is **3.3.0**.

**Why:** OS 3.3 provides a cleaner modern DriverWorks baseline while keeping compatibility with the older OS 3 family that DirectorLink targets.

## ADR-002 — Installation is out of scope

**Decision:** DirectorLink assumes `DirectorLink.c4z` is installed. The project does not care how the user obtained permission/access to install it.

**Consequence:** No jailbreak dependency and no dealer-specific runtime dependency.

## ADR-003 — Director is the runtime dependency

**Decision:** DirectorLink talks to Director from inside a DriverWorks driver.

**Rejected:** Building the core around Composer Pro or the external `/api/v1` Director REST interface.

## ADR-004 — Cloudflare frontend, local control

**Decision:** Host the PWA on Cloudflare Pages, but have the browser connect directly to DirectorLink on the LAN.

**Consequence:** Browser Local Network Access permission and correct CORS/private-network handling are part of onboarding.

**Superseded in part by ADR-026 (0.8.0):** the sites are Cloudflare Workers static assets, deployed by `deploy.yml`.

## ADR-005 — LAN only in V1

**Decision:** No DirectorLink-hosted remote-control relay in V1.

**Superseded by ADR-029 (0.10.0):** optional remote access through api.directorlink.io, sealed end to end.

## ADR-006 — One owner

**Decision:** One paired owner identity/account in V1. Multi-user/roles are deferred.

**Superseded by ADR-025, ADR-027 and ADR-029:** keys have roles, the owner pairs and everyone else is invited.

## ADR-007 — Adapter-based devices

**Decision:** Normalize devices and add explicit proxy-family adapters. Unknown devices remain unsupported rather than receiving guessed commands.

## ADR-008 — DirectorLink owns automation

**Decision:** Scenes, schedules, and automations are DirectorLink-native. Do not import Composer programming/schedules/scenes.

## ADR-009 — Internal scheduler

**Decision:** Do not depend on the Composer Scheduler Agent as the primary automation engine. DirectorLink will persist schedules and execute actions itself using Director timers/time/location APIs.

## ADR-010 — No automatic C4Z update in V1

**Decision:** Updates are manual through Composer initially.

**Extended by ADR-035 (1.1.0):** admins see in the app when a newer release is out, with its download and the Composer steps; installing stays in Composer.

## ADR-011 — Discovery source

**Decision:** Prefer structured DriverWorks tables:
- `C4:GetDevices({})`
- `C4:GetProjectHierarchy()`

rather than parsing the entire project XML when structured APIs already provide the required data.

**Reason:** Less fragile and easier to normalize across versions.

## ADR-012 — User-facing entity identity

**Decision:** Proxy entities are the primary homeowner-facing devices. Backing protocol drivers are retained as relationship metadata and not shown as duplicate controllable entities.

Standalone/combo drivers without proxy relationships may appear as unsupported entities.

## ADR-013 — Apache-2.0

**Decision:** DirectorLink uses Apache License 2.0.


## ADR-014 — GitHub Releases are the binary distribution channel

**Decision:** Do not commit built `DirectorLink.c4z` binaries to `main`. Publish official binaries as versioned GitHub Release assets.

**Why:** Users can clearly upgrade/downgrade, release binaries stay tied to immutable tags, and source history remains clean.

**Release contents:** `DirectorLink.c4z`, `SHA256SUMS.txt`, and release notes.

**Version source:** root `VERSION` file using semantic versioning. Versions with a prerelease suffix such as `-alpha.1` are published as prereleases.

**Since changed (ADR-022):** releases also carry `openapi.json`, and `VERSION` is plain `MAJOR.MINOR.PATCH`, without prerelease suffixes.

**Since changed (ADR-035):** releases up to 1.0.0 were published mutable: their files could still be replaced after publishing. From 1.1.0 on they are immutable, with the repository's immutable-releases setting on: once a release is published, its tag and files cannot change. The app's update notice offers only immutable releases.


## ADR-015 — Start the PWA without a frontend framework

**Decision:** The first DirectorLink PWA is plain HTML, CSS, and JavaScript hosted directly from the repository `app/` directory.

**Why:** The current UI is small, this removes Node/framework dependencies from deployment, and it lets us prove the harder browser-to-LAN transport before committing to a larger frontend stack.

**Cloudflare configuration:** root `web`, build command `exit 0`, output directory `.`. (Superseded by ADR-026: `app/`, `console/` and `site/` are deployed by `deploy.yml`.)

**Revisit:** A framework/build tool may be introduced later if the device dashboard, state management, routing, or component complexity justifies it.


## ADR-016 — Read-only HTTP transport spike on port 41999

**Decision:** Validate browser-to-Director communication with a minimal HTTP/1.1 server implemented on DriverWorks `C4:CreateServer`, listening on fixed TCP port `41999`.

**Why fixed port:** A public browser cannot discover Director's random ephemeral DriverWorks socket port. A known port gives the PWA a deterministic local endpoint without LAN scanning.

**Security:** Read-only routes require a random per-install Bearer token persisted encrypted on Director. CORS is restricted to official DirectorLink origins.

**Status:** Alpha integration decision. Re-evaluate port configurability and final pairing/authentication after testing on real systems.

**Superseded by ADR-019 in 0.2.0.** The fixed port 41999 stays; the read-only alpha routes were replaced by the OpenAPI contract.


## ADR-017 — Control lights through the Light V2 proxy

**Decision:** DirectorLink controls lighting entities by their Light V2 **proxy IDs**, not by sending commands directly to backing protocol drivers.

**State contract:**
- variable 1000 = Light State
- variable 1001 = Light Brightness Percent when the device is dimmable
- variable 1006 = Default On Preset Brightness when available

**Control contract:** On/Off use `SET_BRIGHTNESS_TARGET` with static preset IDs 1/2 and are validated on a real Director. Explicit brightness is adapter-selected: `knx_dimmer.c4i` uses DriverWorks-documented `RAMP_TO_LEVEL` (`LEVEL`, `TIME = 0`); other Light V2 dimmers currently use `SET_BRIGHTNESS_TARGET` with `PERCENT`.

**Why:** The proxy is Control4's abstraction boundary. It lets DirectorLink support Control4, Zigbee, Z-Wave and third-party lighting drivers through one documented interface instead of learning each protocol driver's private command set.

**Safety:** A device is not marked controllable unless its Light V2 state variable exists and DirectorLink can register the required state listener.

**Extended by ADR-033 (1.1.0):** the legacy Light proxy (`light.c4i`) is controlled the same way, through its proxy, with its own commands.


## ADR-018 — One-owner local pairing

**Decision:** V1 uses a short local pairing code to provision one long-lived owner Bearer credential to a browser.

**Owner credential:**
- generated randomly with `C4:UUID("RANDOM")`
- persisted encrypted on Director
- never displayed in Composer after alpha.8
- stored locally by each paired browser

**Pairing code:**
- 8 numeric digits
- visible in the DirectorLink Composer properties
- valid for 15 minutes
- rotated after every successful pairing
- five failed attempts per minute trigger a 60-second lock
- never persisted by the PWA

**Transport:** `POST /v1/pair` is the only unauthenticated application route. The code is sent in the `X-DirectorLink-Pairing-Code` header, not in a URL.

**Why:** Homeowners should not copy long API secrets from Composer. Pairing keeps the long credential private while preserving the local-first, no-cloud-relay architecture.

**Superseded by ADR-021 in 0.2.0.** Pairing now issues named API keys instead of one shared owner credential, and the code moved from a header to the JSON body of `POST /v1/auth/pair`.


## ADR-019 — OpenAPI-first REST API with logical names

**Decision:** `api/openapi.yaml` (OpenAPI 3.1) is the contract for the LAN API. Resources use logical names — `rooms`, `devices`, `lights`, `thermostats`, `logs`, `api-keys` — and state changes are `PATCH` requests with the desired state (`{"on": true}`), answered with `202 Accepted`. Errors use RFC 9457 Problem Details with a stable `code`.

**Why:** A standard description lets any client (the app, Postman, Home Assistant, scripts) use the API without knowing Control4. Control4 command names, proxy IDs and variable numbers stay inside the adapters.

**Consequences:**
- `scripts/check_api.py` fails CI when the spec and `driver/src/api/routes.lua` differ in any method, path or public flag.
- The build embeds the spec so the driver serves it at `/v1/openapi.json`; releases publish it as `openapi.json`.
- The driver uses its own JSON encoder/decoder (`src/core/json.lua`) for deterministic output (explicit `[]` and `null`) and so the API layer can be tested in plain Lua.
- The HTTP server runs without a delimiter and assembles requests itself, so request bodies (`Content-Length`) are supported.

## ADR-020 — One repository for API, driver and app

**Decision:** The API contract, driver and app stay in this repository (`api/`, `driver/`, `app/`), with the app deployed by Cloudflare from `app/`.

**Why:** While the API is changing, most changes touch the spec, driver and app together; one pull request keeps them consistent and CI checks them together. The Jewish-calendar module (later) and the automation engine ship inside the `.c4z` anyway.

**Revisit:** Split a part into its own repository when it gets an independent lifecycle or other consumers (most likely a reusable calendar library, then the app).

## ADR-021 — API keys

**Decision:** Every route except health, the API description and pairing requires `Authorization: Bearer <api key>`. Keys are named, stored on Director (at most 20; encrypted up to 0.8.0, only hashes since 0.9.2 — ADR-028), listed without secrets, and revocable through the API or all at once with the Composer action **Revoke All API Keys**.

**First key (0.2.0):** exchange the 8-digit Composer pairing code at `POST /v1/auth/pair` (15-minute code, rotated after use, 5 failures per minute lock pairing for 60 seconds).

**0.3.0–0.7.0 (replaced by ADR-027):** the first key came from approval in the Control4 app: the driver adds a **DirectorLink Access** experience button (a `uibutton` proxy on binding 5001); a client calls `POST /v1/auth/requests`, the homeowner presses the button within 2 minutes, and the client collects its key once with the secret request id. One request waits at a time, 5 per 10 minutes. The Composer pairing code stays as a fallback.

**Why keys and not an open LAN API:** the API can operate door, gate and garage relays through KNX; without a key anything on the home network could.

## ADR-024 — DirectorLink is a protocol driver with a button proxy, not a combo driver

**Superseded by ADR-027 (0.8.0):** with the button gone, DirectorLink is a combo driver again.

**Decision (0.3.0):** `driver.xml` declares no `<combo>`; the DirectorLink protocol device runs the Lua code and owns one `uibutton` proxy on binding 5001 (**DirectorLink Access**).

**Why:** Real-system testing showed that for a combo driver the Director creates only the combined device and never the extra button proxy. Every working button driver on the test system (door and garage relays, DoorBird, experience buttons) is a protocol device (item type 6) with a `uibutton` child proxy (type 7).

**Consequence:** Moving from the 0.2.x combo layout needs a one-time remove and re-add in Composer. `check_package.py` fails if `<combo>` comes back. Discovery skips the bridge's own proxies.

## ADR-022 — Versions are MAJOR.MINOR.PATCH with one source

**Decision:** `VERSION` holds a plain `MAJOR.MINOR.PATCH` version with no pre-release suffix and is the only version to edit. The build stamps it into `version.lua`, the API description and `driver.xml`, where Control4's integer version is derived as `MAJOR*10000 + MINOR*100 + PATCH`.

**Why:** One place to change, and the Control4 driver version always increases with the release version. `0.x` releases already signal that the project is in development.

## ADR-023 — Driver log served by the API

**Decision:** The driver keeps its last 500 log entries in memory and serves them at `GET /v1/logs` (filters by level, category and sequence number); the level is set with `PATCH /v1/logs/settings` or the Composer **Log Level** property. Entries also go to the Director driver log.

**Scope:** DirectorLink's own log only. Director's system logs are outside the driver sandbox and contain other drivers' data, so they are not exposed over the LAN. Fields such as keys, tokens and pairing codes are redacted before logging.

## ADR-025 — API keys have roles; doors need a Composer switch

**Context:** One kind of key could do everything, including opening doors and creating more keys. Remote access (next) and family members need less than that.

**Decision (0.7.0):** Four ordered roles — `viewer`, `member`, `doors`, `admin` — each allowed everything the ones before it are. Every non-public route in `routes.lua` names the least role it needs, and the OpenAPI operation states the same as `x-directorlink-role`; `check_api.py` fails the build when they differ or when a restricted operation does not document 403. Keys from before roles existed become `admin`; the Composer pairing code issues `admin`; access requests default to `admin` for a home's first key and `member` afterwards, and Composer shows the requested role before the homeowner presses the button. The last admin key cannot be demoted. Opening doors additionally needs the Composer property **Door Control** = Enabled (default Disabled).

**Consequence:** Remote users will map onto the same roles. The app should read `GET /v1/api-keys/current` and hide what the key may not do.

## ADR-026 — The project is DirectorLink, on directorlink.io

**Context:** "C4Bridge" leaned on the Control4 name and the project needed an international brand before it has outside users and accounts. The API console had grown into a developer tool of its own inside the app.

**Decision (0.8.0):** The project, driver and API are named **DirectorLink** (slogan: *Direct to Director. End-to-end integration. Open source.*), on `directorlink.io`. The driver package is `DirectorLink.c4z` and its button **DirectorLink Access**. The repository holds three static sites, each its own Cloudflare Worker with a custom domain: `app/` (formerly `web/`) on `app.directorlink.io`, `console/` (API console, debugging, logs, key management) on `console.directorlink.io`, and `site/` (landing page) on `directorlink.io`. GitHub Actions deploys them (`deploy.yml`) instead of dashboard-configured builds, so the deployment is part of the repository. Past release notes and the validation log keep the old name as written.

**Consequence:** Control4 sees DirectorLink as a different driver: moving from C4Bridge means removing it and adding DirectorLink, so API keys, room names and the Door Control setting start fresh. The driver's CORS allowlist is the two new sites plus localhost (localhost removed in 1.0.0, ADR-032); the old `app.c4bridge.io` no longer reaches a DirectorLink controller.

## ADR-027 — Owners pair once with an on-demand code; everyone else is invited

**Context:** 0.3.0–0.7.0 approved each new browser with a button in the Control4 app. That needed a child proxy (so DirectorLink could not be a single device), a workaround to make the button visible, and an approval for every phone. With accounts and remote access coming, only the owner should ever need to prove control of the project.

**Decision (0.8.0):** The button and access requests are removed; DirectorLink is again a single self-contained device (combo driver with its own proxy). The first key comes from a pairing code created on demand with the Composer action **New Pairing Code** (automatically while the driver has no keys): shown as `1234 5678`, valid 15 minutes, works once, rate-limited (5 wrong codes → 60 s lock), and always `admin` — Composer access already means full control. Further keys are created by an admin. With remote access (planned): the owner signs in with Google or Apple and claims the home on the LAN with a pairing code; family members join by an invitation tied to the invited email (single use, 7 days; the owner approves when the accepting account's email differs); roles are the same as for API keys. Home-network use without an account stays possible.

**Consequence:** Installers read the code for homeowners without Composer. Replaces the approval flow of ADR-021 and the protocol-driver-with-button layout of ADR-024. The Composer properties are reduced to what an installer needs; the load history moves to `GET /v1/system` and the console.

## ADR-028 — Stored data is written as `json:` plus JSON; keys are kept as hashes

**Context:** Up to 0.9.1, DirectorLink lost its API keys and its remote-access identity whenever the driver reloaded, and room names were read by the same kind of code. On the test controller (OS 3.4.3) the values were saved — they are in Director's `state.db` — but `C4:PersistGetValue` returned a stored JSON string decoded into a Lua table, and DirectorLink accepted only a string, so it started empty. Values that are not JSON (the load and pairing counters) came back as written, which hid the problem. The keys that 0.8.0 kept encrypted were lost on update too; whether they also came back decoded or could not be decrypted (Director logs "has no driverKey" at every load of the driver) was not established.

**Decision (0.9.2):** `src/core/store.lua` writes every stored value as `json:` followed by JSON, which Director returns unchanged, and accepts tables Director has already decoded, so data written by 0.9.1 and older is read and then rewritten. Keys are kept in plain persistence as SHA-256 hashes (SHA-1 on a controller without SHA-256; each key records its algorithm). A presented key is hashed and compared in constant time; the key itself exists only in the response that creates it. Keys in the encrypted store of 0.8.0 and 0.9.0 are moved when Director can read that store, which is then emptied. The remote-access identity is kept in plain persistence as well: its secret has to be sent to the relay, so it cannot be kept as a hash.

**Consequence:** Keys, room names and the home identity survive driver updates and restarts, and each load logs how the keys came back (`keys loaded`, `stored_as`). Whoever can read the driver's stored data (root on the controller, possibly a project backup) finds only hashes of long random keys, which cannot be turned back into keys. The home secret is readable there; that is acceptable while remote access is a read-only test, and is revisited when claiming a home with a pairing code replaces trust on first use. The fake Director in the driver tests decodes stored JSON the same way. (Since ADR-029 each key's lock key is stored too; ADR-032 lets the owner replace the home secret and says what such a copy allows.)

## ADR-053 — A new device joins by approval from another device of the account; Paste invitation link

**Context:** Alerts on iPhone need DirectorLink on the Home Screen (ADR-047), and iOS gives that app its own storage: it signs in again there and has no key. iOS also opens every link in Safari, so the link and QR code of Add my other device never reach it, and pairing on the home network is blocked there (WebKit). A first fix that only pasted the link was set aside at the owner's request: they wanted a way without a link.

**Decision (1.7.0):**
- **Join from another device.** On the Connect screen, signed in, a device without a key asks to join one of its account's homes (`POST /v1/homes/{home_id}/device-requests`), with a label from its browser's own description ("Safari on iPhone", "Home Screen app on iPhone"). A device of the same account that reaches the home with an admin key (the rule of Add my other device; its role read from the controller, as Settings asks, before it looks) sees the request while the app is open, under the header of every screen: it looks every 60 s while shown, at once when it comes to the front or connects, and every 2 s only while it answers one. No push in this release.
- **A code that nobody in between can choose, typed on the approving device.** The new device makes an X25519 key pair (WebCrypto, or the app's own ladder where WebCrypto has no X25519) and sends first only a commitment: SHA-256 over its public key. **Show code** on the other device sends that device's own public key; only then does the new device send its key, which the cloud and the other device check against the commitment. Both devices work out six digits from the request id and both keys. The new device shows them; the approving device asks for them and never shows its own: the person types what the new device shows, and only the same digits approve, so a tap cannot approve without the asking device in sight. A wrong code approves nothing; the third wrong code declines the request. This refines the lead's design (a code from the new device's key alone): six digits from one key can be matched by trying about a million keys, seconds of work, so whoever passes the keys on (the cloud too) could put in its own and show the same code. With the commitment each key is fixed before the other is seen, and a key put in the middle gives each screen its own code (one chance in a million to match). The new device keeps the first approving key it saw and withdraws the request if it changes; the approving device keeps the commitment it saw before it sent its key. A new device that gets a key another way while its request waits (it pairs at home, or opens an invitation's link) withdraws the request when it connects with that key, and one that had a key by the time the invitation came opens the join page and asks before replacing it.
- **Approve** makes a for-me invitation at the controller exactly as Add my other device does (the same code in the app: the device's role, 10 minutes, `for_me`, the account's email, registered by the controller), and seals `home.invitation.secret` to the new device: X25519 with a key pair of its own, HKDF-SHA-256 over the request, the home and both keys, AES-256-GCM. Both ends are browsers with WebCrypto, so GCM is fine here (the controller's crypto, ADR-048, has only CBC). The cloud keeps the sealed value and hands it once to the new device (`collect`), which opens it and joins as with the link. The controller sees an ordinary for-me invitation and join: nothing changes in the driver, and a 1.6.0 driver works. The approving device revokes the invitation at home when the cloud refuses Approve (a 4xx answer); when no answer comes, it reads the request first and keeps the invitation if the cloud took it (approved, or already collected), since the new device may be joining with it.
- **The cloud** (`cloud/src/device-requests.js`, D1 `device_requests`, migration `0009`): only the account's own sessions see or change its requests; the account must belong to the home; Show code and Approve need an account that uses a key there (`member_keys`); asking needs an account that could approve (a key there, an admin key when the controller names its admins; else `409 NO_APPROVER`, and the app says to ask an admin for an invitation). A request lasts 10 minutes and goes when collected, declined, withdrawn, read after it expired, at the daily cron, when the account leaves the home or signs out everywhere. An account has at most 3 open and starts at most 10 an hour (`429 DEVICE_REQUEST_LIMIT_REACHED`). The label is at most 48 characters, without control or direction marks.
- **Paste invitation link**, on the Connect screen and in Settings → Account, reads the clipboard (`navigator.clipboard.readText`; iOS shows its Paste button) and, where that is refused, missing or holds no link, shows a field. It takes a whole link, a message with one in it, or only the part after `#/join/`, and opens the join page as the link would.
- **Older servers:** `GET /v1/me` says `device_requests: true`. Without it the app shows no Join from another device and asks nothing: a 1.6.0 Worker answers unknown paths without CORS, which a browser cannot tell from being offline. Paste works with any server.

**Why:** No link means nothing for iOS to open in Safari and nothing to carry between one's own devices; a device the person already holds approves, which is what Add my other device already proves, without the QR code. The code, typed rather than only compared, because a stolen session can ask under the app's own label ("Home Screen app on iPhone"), and an Approve beside a code invites a tap without looking; the code keeps "the cloud can route, but not read" (docs/ACCOUNTS.md): an approval vouched for only by the cloud would let a dishonest cloud, or someone with its database and a session, put in its own key and read the invitation. The commitment rather than a longer code, because six digits are easy to compare, and a longer code only makes the search longer. The label, because a request must say which device asks; the cloud already knows that the account uses the home.

**Consequence:** For each request the cloud sees the label (the browser and the kind of device), a commitment, two public keys, the sealed invitation it cannot open, and when. Someone with the account's session can ask, under any label: the account's devices then show a request nobody expected, with "Didn't ask? Decline it and sign out everywhere in Settings → Account."; approving it takes the code on the asker's own screen, which the owner does not see, so a careless tap approves nothing; the request ends within 10 minutes, or at once with Decline or Sign out everywhere (which ends that session too). A device that reaches the home asks the cloud once a minute while the app is shown: about 1,440 Worker requests a day, each with two D1 reads, for a screen left open all day. Only devices with an admin key can approve, as only they can make invitations; a member's new device is invited by an admin (and Paste brings that link into the Home Screen app). Both devices must have the app open for the minute it takes. An app before 1.7.0 shows no requests; the new device's request then runs out. Migration `0009` goes before the Worker that uses it.

## ADR-052 — DirectorLink in numbers: three public totals, counted once an hour, on the website from 25 homes

**Context:** The owner wants directorlink.io to say how many use DirectorLink: homes and people with an account, and driver downloads. The account service knows which homes are claimed and which accounts exist; GitHub counts the downloads of each release's files. Nothing about any one home may become public, and the homes must not send anything new for it (no device counts). Today there are 2 linked homes, 5 accounts and 34 downloads: numbers that small say little on a landing page. The website was a static page without scripts (CSP `script-src 'none'`, `connect-src 'none'`).

**Decision (1.7.0):**
- **Three totals, counted once an hour by the account service** (`cloud/src/stats.js`): *homes*, the homes linked to an account (claimed, their owner's account still there; D1 keeps no time a home was last connected, so a home stays counted from its claim until its owner's account is deleted: a controller reset with Reset Remote Identity, replaced, or used for testing counts on, and the total is homes ever linked whose owner's account remains, not homes in use); *people*, the accounts someone can sign in to (an account Apple's notices left without a sign-in, kept for its home or for 90 days, is no one's, ADR-041); *downloads*, the `download_count` of `DirectorLink.c4z` summed over every release in GitHub's public releases list (pages of 100, at most 10; checksums, the API description and other names do not count). Kept in D1 (`stats`, migration 0010), each with the time it was counted. The cron is a second trigger, `47 * * * *`, beside the daily `17 3 * * *`; `scheduled` tells them apart by `event.cron`, as Cloudflare documents (5 triggers an account on the Free plan, 250 on Paid).
- **A count that fails keeps the last total.** Homes and people are counted and written in one D1 batch (both or neither), the downloads on their own: when D1 or GitHub fails (unreachable, an error, a rate limit, an answer that is not a list of releases with counts), that total and its time stay as they were and the log says why (`stats_not_counted`). A partial sum over some pages is never kept. GitHub is asked without a token, with a User-Agent; an optional `GITHUB_TOKEN` secret is sent when set. `GITHUB_API_URL` points the tests at a fake GitHub.
- **`GET /v1/stats`, public:** `{"homes", "people", "downloads", "updated"}`, `updated` being when the oldest of the three was counted. No cookie, no key, GET only (and its preflight), CORS without credentials for the website's origins (`SITE_ORIGINS`: directorlink.io and www), `Cache-Control: public, max-age=300`. Until all three have been counted once: 503 `STATS_NOT_COUNTED`; D1 unreadable: 503 `STATS_UNAVAILABLE`. Nothing else is in the answer.
- **The website** gets its first script, `site/numbers.js`: it asks once at load, without cookies or referrer, and fills in the section "DirectorLink in numbers" only when the answer is three counts and homes are at least 25. The section is `hidden` in the page and `display: none` until then: on an error, a refusal, a slow answer (8 s) or fewer homes nothing shows and nothing moves. It is the page's last section, so showing it moves only the footer. CSP: `script-src 'self'`, `connect-src https://api.directorlink.io`, nothing more; `check_sites.py` holds these rules (one script, a module, only on the home page; only the totals' address in it; the 25; no storage, no HTML from the answer). English only, in the site's light and dark.

**Why:** Hourly totals from the account service, because it already has them and they change slowly; counting on each request would let anyone watch an account or a home appear within seconds. Accounts that can sign in, because an account kept only for its home after its person left (ADR-041) is nobody using DirectorLink. Only the package's downloads, because the checksums and the API description are fetched by scripts, and the update check reads the release, not its files. 25 homes, the owner's rule, because a handful of homes says little and invites guessing whose they are. A second trigger rather than an hourly one doing the daily work at 03:00, because the daily housekeeping and its tests stay as they are. D1, because the totals must outlive a failed hour and every isolate must give the same answer. A script on the website, because the totals change hourly and the site deploys only with a commit; it is the site's own file under its CSP, and the browser reaches nothing but the totals.

**Consequence:** Public now: three totals that change at most once an hour, readable by anyone at `/v1/stats`, also while the website does not show them (the 25 homes are the website's rule; the endpoint answers below them too). With few homes, a total that changed between two hours tells that some home was linked or left, or some account was made or deleted, in that hour, never which. Nothing new leaves a home. A visitor's browser now asks api.directorlink.io for the totals (no cookie, no referrer), which Cloudflare logs like any request; the privacy page says so. GitHub limits requests without a token to 60 an hour per address, and Workers share their addresses: if the downloads stop being counted (`stats_not_counted`, status 403 or 429), set `GITHUB_TOKEN` (a fine-grained token with no permissions). Cost: 24 runs a day, each two or three requests to GitHub and two D1 writes; one D1 read of three rows per visit that is not cached. The site deploys with every push to main and the Worker by hand: until the Worker has `/v1/stats` and has counted once, the site gets 404 or 503 and shows nothing. Migration 0010 must be applied before the Worker that uses it is deployed.

## ADR-051 — Scene links: a private link per scene for the phone's own automations, never for doors or gates

**Context:** The owner wants scenes to run from the phone's own automations: iPhone Shortcuts ("when I arrive home", Siri, an NFC tag automation), Android automation apps (HTTP Shortcuts, Tasker, MacroDroid), or an NFC tag opened in a browser. These cannot seal a request (they hold no key and have no WebCrypto), and a phone running an automation is anywhere, so the request has to go through the account service, which until now never saw anything it could use (docs/ACCOUNTS.md, "Who knows what"). The owner's rules: never for scenes that open doors or gates; links can be revoked; every run is in History. Cloudflare documents that Workers Logs, which is on for the Worker (`cloud/wrangler.jsonc` observability), keeps an invocation log for every request, with "a message describing the request method and the request URL" ([Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)); it documents the redaction of IDs in URLs and of sensitive headers only for Tail Workers' events ([Tail Handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/tail/)), where the request an event carries has its URL, method and headers, not its body.

**Decision (1.7.0):**
- **One link per scene, made by admins.** The scene editor's *Link for automations* opens the scene's link screen (`#/scene/<id>/link`), which makes, replaces and removes it (`POST`, `GET`, `DELETE /v1/scenes/{id}/link`); `GET /v1/scene-links` lists them (Scenes → *Links for automations*, `#/links`). The controller makes a link id (8 hex digits, not secret) and a secret of 160 random bits (40 hex digits, `src/core/random.lua`), and keeps only the secret's SHA-256 (SHA-1 on a controller without it), as it keeps API keys (ADR-028), with the home id the link's address names (`src/core/scene_links.lua`, store `directorlink_scene_links`). The secret is in the answer that makes the link and nowhere else; the app shows it once, with Copy buttons, a QR code and the steps for iPhone Shortcuts, Android and an NFC tag, keeps it in memory only and forgets it when the screen is left. Making a new link replaces the old one, which stops working at once. An optional label (up to 64 characters, "Arriving home") names the link in History.
- **A link goes with the key that made it.** The controller keeps that key's id with the link (`made_by` in the list). Revoking the key (Revoke in People and devices, Remove a person, Forget access key or Pair again on that device) or its expiry removes its links (History `link_removed`, `reason` `key_gone`), and the app's question before revoking says how many links stop with it. Composer's **Revoke All API Keys** removes every link (`links_removed`, `reason` `keys_revoked`). A link made by a test build of 1.7.0, before the key was kept with it, names no key: only Revoke All API Keys, Remove All Scene Links, Reset Remote Identity or removing it ends it.
- **Only what a link may run, never doors or gates.** A link runs only a scene whose steps are all of an allowed type (`SceneLinks.ALLOWED`: lights, climate, fans, blinds, music, refrigerators). Doors and gates (`relays`) are refused, and so is a step type added later until it is put on one list or the other (`test_scene_links` fails while a step type is on neither). A scene with any other step gets no link (`409 SCENE_OPENS_DOORS`). A change that adds one removes the scene's link (the app warns in Add an action and asks before saving; History says why), and so does deleting the scene. Every run checks again, and runs the scene as a member's key would (`{ id = "link:<id>", role = "member" }`, as schedules run), which skips doors and gates anyway. At every start, links whose scene is gone or opens doors (changed by an older DirectorLink) go.
- **What it needs.** Remote Access on and a home the relay has accepted (`409 REMOTE_ACCESS_OFF`, `HOME_NOT_LINKED`; the app says which), and at run time a home an account has claimed (the Worker checks D1).
- **The address, and where the secret goes.** `https://api.directorlink.io/run/<home_id>.<link_id>`. An automation sends a **POST** with the secret **in the body**: `{"secret": "…"}` (Shortcuts: Get Contents of URL, Method POST, Request Body JSON, one Text field `secret`), a form field `secret`, or the secret alone as text (Android apps); the whole link pasted in place of the secret works too. A browser (an NFC tag, a tap) gets the link with the secret after `#`, which browsers never send: a **GET** answers a small page with one Run button whose script posts the secret. A GET never runs anything, because link previews (Messages, WhatsApp, Slack) fetch links, and the page is the same for every address, a made-up one too: it names neither the home nor the scene (`no-store`, `noindex`, `no-referrer`, a strict CSP with a nonce).
- **Through the relay.** The Worker (`cloud/src/scene-links.js`) checks the address and the secret's shape, then that the home is claimed, and hands the link and the phone's address (`CF-Connecting-IP`) to the home's Durable Object. The object answers `429 TOO_MANY_RUNS` to an address (an IPv6 one by its /64) whose runs were answered 404 ten times in 10 minutes, until the first of those is 10 minutes old, before its run reaches the home or counts against the home's limit (at most 1,000 addresses a home are remembered, in memory only, never logged); it lets at most 30 runs a minute reach the home (`429 TOO_MANY_RUNS`, `Retry-After`) and sends `{"type":"link","id","link","secret"}` (docs/RELAY.md) only to a driver whose `hello` lists `features: ["scene_links"]`. The controller hashes the secret, compares it in constant time, allows 6 runs a minute a link, runs the scene and answers `link_result`: `ok` with `result` `ran`, `partly` (some devices skipped or failed), `failed` (none ran) or `nothing` (there was nothing to run: its devices were removed in Composer), or `NOT_FOUND` for an unknown link, a wrong secret, a scene gone or with doors and a key gone alike, or `RATE_LIMITED` with `retry_s`. The phone gets `200 {"result", "message"}`, `404` for an unknown home, link or secret word for word alike, `429`, `503 HOME_OFFLINE`, `502`/`504`. The secret is never logged, by the Worker or the driver (refused runs: one log line a minute at most, with the link's id). The Worker logs each run (`link_run`: the home, the link's id, the status, the result word, why and how long), as it logs every relayed message.
- **A driver before 1.7.0** ignores message types it does not know (it logs `ignored relay message` at debug level and answers nothing; the phone would wait 15 s for a 504). It sends no `features` in its hello, so it is never sent a run: the phone gets `404` at once. A 1.7.0 app against it shows nothing of links (`features.scene_links` in `GET /v1/system`).
- **History** (ADR-046): each run is `scene` `run` with `who` `{type: "link", link_id, name: <label>}` and the devices' counts; making, replacing and removing a link are `access` entries (`link_created`, `link_replaced`, `link_removed`, with the scene's name, the label and, when a link went by itself, why: `doors`, `scene_gone`, `other_home`), and Composer's new action **Remove All Scene Links**, Revoke All API Keys and Reset Remote Identity (whose new home id the addresses do not name) are `links_removed`. A link that went with its key is `link_removed` with `reason` `key_gone`. When Remove All Scene Links cannot write the store, the links stay (in memory as in the store, so a restart changes nothing) and History (`links_removed` with `outcome` `failed`), the log and Composer's Remote Status ("Scene links not removed: could not save") say so. A refused run is not an entry: a flood would push the month out. Composer's Last Automation says "run from a scene link (label)".
- **In backups, as hashes**, like the keys' (ADR-042): section `scene_links`, each with the key that made it. A restore follows the keys' rule: the backup's links come back only when its keys do (the driver added again or the controller replaced, with only the restoring device paired: what keeps the family's tags and Shortcuts working; from a backup made before 1.7.0, the links on the controller); otherwise the controller's links stay as they are, so a link removed or replaced since the backup was made never comes back and its replacement keeps working. Either way, only the links whose scene comes back without doors or gates, that were made for the home identity in use after the restore (the address names it), and whose key is among the keys after it (one this device replaces, `replaces_key`, passes its links to this device's key).

**Why:** The phone's automations are where "when I arrive home" lives; DirectorLink cannot run them, and they cannot seal. A link per scene, not per person or key: one scene is what it can do, and a scene the admin chose, never a door. A long random secret kept as a hash, because then a copy of the controller's data or a backup cannot run anything, and the link can be replaced like a key. The secret in the body, not in the address, because Workers Logs record request URLs and their redaction there is not documented, while nothing Cloudflare documents records a request's body; after `#` for browsers, because then it never leaves the phone's browser except in the page's POST. Two Copy buttons and a JSON field make the Shortcuts setup a minute's work; a header would take as many steps and is no safer by documentation. 404 for everything unknown, so the answers tell nothing about which links exist; the feature in the hello, so an older driver is never asked to answer what it does not know. In backups because a family's NFC tags and Shortcuts should survive a replaced controller, and a hash of 160 random bits tells whoever has the backup nothing (the backup already holds the lock keys and the home secret); only with the keys, because a restore that keeps the keys (ADR-042) must not bring back a link that was removed for a reason either. With the key that made it, because revoking a person's key is how an admin cuts them off, and Revoke All API Keys is the installer's switch for when keys cannot be trusted (ADR-043). An allowlist of step types, not a list of what opens doors, so that a step type added later is not linkable by default. A limit per address on wrong guesses, so one stranger cannot keep the family's runs at 429; in memory, as the home's limit, because it only has to last minutes.

**Consequence:** This is the first thing the account service sees in the clear: whoever holds a link can run that one scene, from anywhere, until it is removed or replaced or the key that made it is revoked, and the account service sees the link and its secret in transit when it is used (not which scene: the cloud has no names), with when and the result word. It keeps no secret, but each run is a `link_run` line in Workers Logs (the home, the link's id, the status, the result word, why and how long), kept there for some days (Cloudflare documents 3 on Workers Free, 7 on Paid), next to Cloudflare's own line for the request (its address and the phone's IP address). docs/ACCOUNTS.md says so in "Who knows what", and the privacy page too. Someone who controlled api.directorlink.io (or Cloudflare) could run a linked scene with a secret it saw; scenes with doors or gates can never be linked, so that is at most lights, AC, fans, blinds, music and refrigerator settings. A lost secret cannot be shown again: replace the link. Home ids are not secret: every link, NFC tag and invitation link (`#/join/<home_id>.…`) carries one, so every past guest and member has it. The limits are kept in the Durable Object's memory (a flood keeps it awake): from one address, someone guessing uses at most 10 of the home's runs in 10 minutes, but many addresses together can still use up its 30 a minute, and the family's runs get 429 meanwhile; the family behind the guesser's address (the same Wi-Fi, a carrier's shared address) gets 429 too, for up to 10 minutes. An offline home answers 503, not 404, because the family needs to know: so whoever knows a claimed home's id can tell whether it is online, and a claimed, online home's 404 takes the controller's round trip while an unknown or unclaimed one's does not. The controller is not told when another account claims the home (a sold house, docs/ACCOUNTS.md): the old family's links keep working, so the new owner should run **Revoke All API Keys** in Composer, which now ends every link too (Reset Remote Identity also does). The account service does a D1 read for each POST that has a secret's shape. Going back to 1.6.0 keeps the links' store unread and the relay sends no runs; History entries of link runs are left out by 1.6.0's history (it does not know `who` `link`); a scene changed there to open doors loses its link at the next 1.7.0 start. No D1 migration; the Worker and the driver can be deployed in either order (a link of a 1.7.0 driver answers 404 until the Worker has `/run`). Not yet seen on a real controller or phone: Shortcuts' Get Contents of URL with JSON, and an NFC tag on iPhone and Android.

## ADR-050 — Alerts sealed to each device's key: doorbells, doors opened, the refrigerator, per-kind choices, for every role

**Context:** The alerts of 1.6.0 (ADR-047) go to admins only, for two things, and say only their kind and time, because the cloud composes them and must not learn names. The family wants a doorbell ring on the phone with the app closed (the app noticed rings only while open, from `last_ring_at` in its doorbell polls), the owner wants to know when a door or gate is opened and by whom, members want the refrigerator door left open (ADR-049), and each device should get only what its person chose. A ring is the DoorBird driver's event on the controller; who opened a door is what the history already records (ADR-046). The cloud knows which account uses which key id (`member_keys`) and which key ids are admin keys, nothing more.

**Decision (1.7.0):**
- **The controller decides, and seals.** For what it alerts about (a doorbell rang, a door or gate was opened, the refrigerator's door was left open, a schedule failed) the driver (`src/cloud/alerts.lua`) sends one relay message, `{"type":"notify","at":"<time>","for":{"<key id>":{"iv","ct","mac"}, …},"brief":true?}` (docs/RELAY.md), only while connected. Each part is sealed to one key: its alert key `HMAC-SHA256(lock key, "DirectorLink alert v1")` (ADR-029's lock key), its `enc` and `mac` keys `HMAC-SHA256(alert key, "enc" / "mac")`, AES-256-CBC with a random IV, then HMAC-SHA256 over `"alert v1|" + home + "|" + key id + "|" + iv + "|" + ct`, through C4:Encrypt and C4:HMAC as lock.lua does (`tests/vectors/alert.json`, made with Node's crypto, reproduced by the driver and opened by the app's worker). Inside: the kind, the time, the device's id, name, room and room id, and for a door who opened it as the history names them (the key's device and person, the scene, or Control4), for the refrigerator for how many whole minutes at least its door has been open (when known: ADR-049), for a schedule its scene's name; names cut to 60 bytes. *Refinement:* every detail is padded with spaces to 496 bytes before it is sealed, so that every part is 512 bytes (684 in base64) whatever its kind and names (their natural lengths told the kind apart); one that does not fit (quotes and backslashes take two bytes in JSON) has its names shortened, the longest first, whole characters, never dropped. The cloud sees the key ids, the time and whether the alert is `brief`, never a name; what that tells it of the kind is in the Consequence.
- **Who gets what.** A key whose role may get the kind: a doorbell everyone who may see it (every role), the refrigerator members and up, doors opened and schedules that failed admins; whose device switched alerts on; and whose own choices include the kind. Choices are each key's, kept on the controller (`directorlink_alert_choices`, pruned with the keys), read and set by that key only: `GET` and `PUT /v1/alerts/choices` (`{ on, kinds }`; sealed in the app, as every request). Until a key chooses, every kind but doors opened. The answer lists only the kinds its role may get that the home has (a doorbell, a door or gate, a refrigerator), which is what the app shows; `features.alert_choices` in `GET /v1/system` says the driver has all this. *Refinement:* the device's switch is told to the controller (`on`), so that a key whose device never switched alerts on is never in a `notify`, and a home where nobody did sends none (the lead's design included every key the role allowed).
- **Doorbells.** From the DoorBird's ring event (102) on the controller, not from the app's polls; at most one per doorbell in 30 s. `brief`: the cloud asks the push service to keep it 60 s (a ring heard later is no use), Urgency high like every alert. The worker shows it under the tag of the app's own ring notification (`doorbell-<id>`) with the ring's time, and opens Home (its banner) when tapped, as the app's notification does. A push must always show a notification (Chrome shows its own "updated in the background" notice for one that shows none; WebKit revokes the subscription of a site that keeps doing it), so nothing is skipped: a ring the app already shows, or shows on its banner because it is open in front, is shown again in its place silently (`renotify` false, `silent`); and the app does not show a ring the alert already shows.
- **Doors and gates opened** (admins, off until chosen): every `door` entry the history records that opens one (a pulse, by a key or a scene; a relay held open; the gate at a doorbell), and openings DirectorLink did not make but sees: a KNX relay reporting that it closed (its pulse) when it last reported open, and the DoorBird reporting its relay triggered (104), more than 15 s after DirectorLink's own last command to that device. Those go into the history too, with `who` `control4` (the app says "In Control4"), at most one a door a minute, and from there to the alert. *Refinement:* a relay that reports "closed" again without a change (a status read after a restart, a report repeated by its KNX driver) opened nothing, nor does its first report after the driver starts, before its state is known. At most one alert a door a minute. Tapping one opens History.
- **The refrigerator's door** (members and up): `Alerts.fridgeDoor(device, seconds)` is the one function the refrigerator's integration calls (ADR-049; `seconds` since DirectorLink saw the door open, so the alert says "for at least N min"), at most once a refrigerator in 5 minutes; `hasFridge` in `Alerts.start` (main.lua) says the home has one, so that members are offered the choice. *Refinement:* tapping it opens the refrigerator's room, not History, which members cannot open.
- **A schedule that failed** goes sealed from 1.7.0, with its scene's name, at most three an hour (the controller counts now; the cloud cannot see the kind). 1.7.0 drivers no longer send `{"type":"alert"}`.
- **Bounds.** The controller sends at most 60 alerts an hour; the cloud delivers at most 60 `notify` messages an hour a home (a controller that misbehaves), and at most 50 keys in one.
- **The cloud** (`cloud/src/alerts.js`, migration `0008`): `push_subscriptions` gains `key_id` and `offline`. The app registers with its key id (`POST /v1/homes/{home_id}/alerts`, `key_id`, `offline`); the cloud takes it from any account that uses that key at the home (`member_keys`; else `403 KEY_NOT_LINKED`, and the app makes one sealed request through the account and tries again; the home's object records the key after it answered that request, so a registration first waits for the key work it has queued, and when that request does not reach the home the app says so rather than "link this device"), so registering is open to every role. Each part of a `notify` goes, at once and without an alarm, to the browsers registered with its key id by an account that uses that key there, with that part; to nobody else. Offline alerts stay the cloud's and admin-only, without detail: to browsers registered with an admin key that want them (`offline`, the one choice the cloud keeps, as only the cloud can alert when the home is away), and to browsers an app before 1.7.0 registered (no key id) of accounts with an admin key, as before. A 1.6.0 driver's `{"type":"alert","kind":"schedule_failed"}` still reaches the admins' browsers, registered either way. A key gone from the controller's list takes its browsers' registrations with it.
- **One size.** Every push, the cloud's own included, is padded to 1,024 bytes (was 128): a sealed alert is about 900, Web Push takes some 3,990.
- **The app.** Settings → Controller → Alerts on this device for every role with a 1.7.0 controller (admins only, as 1.6.0, with an older one); once on, a switch per kind the controller offers, and for admins the offline alert. Switching on registers the browser and tells the controller (`on`); a controller that cannot be told leaves alerts off. At every start, a controller that does not know this device has alerts on is told again (an app before 1.7.0 switched them on, or a controller was restored). For the service worker the app keeps, in Cache Storage (`directorlink-alerts`), the words in its language and this device's alert key (`/alert-key.json`: the home, the key id and the alert key; never the lock key or the API key). The worker checks the MAC before it decrypts, writes the sentence from the app's words, and shows the general words of ADR-047 for anything it cannot open or does not know.

**Why:** Sealing to each key keeps "the cloud can route, but not read" (docs/ACCOUNTS.md) while alerts start naming things: the cloud delivers what it cannot read, as it relays requests. The controller decides who, because roles and names are its own (ADR-025). One key per part, derived from the lock key, because the controller already has every key's lock key, and a separate label keeps an alert key from opening anything else. Only keys whose device switched alerts on, because a ring then tells the cloud nothing for homes and devices that never asked. The worker keeps only the alert key, because it needs something to open alerts with the app closed, and that key opens alerts and nothing more. The history's door entries, because "doors and gates opened" is what History already records, with who. A short lifetime for rings only, because a late ring is worse than none; and silent replacement rather than skipping, because skipping a push costs the subscription.

**Consequence:** What the cloud now learns: that a home notified certain key ids at a time, and whether the notice was brief; every part has the same size. It never learns a name, which doorbell, door or refrigerator, who opened a door or which schedule, but the keys and the brevity tell it some kinds for certain: a brief notice is a doorbell's ring (the only brief one); a notice that is not brief and names a key that is not an admin key is the refrigerator's door left open (doors opened and schedules that failed go to admin keys only, and the cloud knows which keys those are, ADR-047); one for admin keys only is a door or gate opened, a schedule that failed or the refrigerator. The push services see each push's lifetime (`TTL`) too, so a brief one is likely a ring; nothing more. The cloud could deliver an old sealed alert again to the same device; it shows its own time. The alert key in Cache Storage can be read by any script of app.directorlink.io, as the API key in its storage can (docs/ACCOUNTS.md, *What the lock does not protect*). Alerts are not queued while the home is away (the offline alert says so). A browser registered by an app before 1.7.0 gets offline alerts, and a 1.6.0 driver's schedule alerts, until the app starts once after the update, which registers it with its key; with a 1.7.0 driver its schedule alerts are sealed and wait for that too. A 1.7.0 app with a 1.6.0 driver shows the 1.6.0 switch for admins only. A driver going back to 1.6.0 leaves the choices store unread and drops the Control4 openings from the history, which it does not know; the rest of the history stays. An app before 1.7.0 shows a Control4 opening as DirectorLink's. The choices are not in backups: a controller restored from one has none, and each device's app tells it again at its next start (the kinds then as by default). After DirectorLink starts, a KNX relay's first opening in Control4 is not seen unless the relay reported a state before it. Migration `0008` must be applied before the Worker that uses it is deployed; the Worker of 1.6.0 runs on it unchanged. Not yet seen on a real controller: the DoorBird's relay event (104) after a press in its own app or a keypad, and a KNX relay's event for a pulse made in Control4.

## ADR-049 — Samsung refrigerators, through the owner's own refrigerator driver

**Context:** The owner is adding a Samsung refrigerator, controlled in Control4 by his own driver, Samsung Refrigerator (DirectorLink) 1.0.0 (`DirectorLink-Samsung-Refrigerator.c4z`, a separate repository). That driver talks to Samsung's SmartThings cloud and shows five uibutton tiles in the Control4 app: the refrigerator's status and Power Cool, Power Freeze, Sabbath Mode and Ice Maker. It keeps the state in twelve variables of its own, added in this order (so Director numbers them from 1001): POWER_COOL, POWER_FREEZE, SABBATH_MODE, ICE_MAKER, ONLINE, DOOR_OPEN, FRIDGE_TEMP, FREEZER_TEMP, FRIDGE_SETPOINT, FREEZER_SETPOINT, POWER_W, WATER_FILTER_USAGE. Its command SET_FEATURE {Feature, State} goes through the cloud; it changes a variable only once the refrigerator confirms (about 4 s), and fires Command Failed after about a minute without. Its event 15, Door Left Open, fires once per opening after the Composer property Door Open Alert (5 minutes by default); doors are read at its poll interval (2 minutes). Which features a model has, and the unit of its temperatures, are only in Composer properties, which another driver cannot read; every variable starts at 0 and stays there for what the refrigerator lacks. A family that keeps Shabbat wants Sabbath Mode switched on and off by a schedule.

**Decision (1.7.0):**
- **One device in its room.** Discovery recognises the driver by its file name like the other drivers it knows (any case, and Composer's copy of a second download, `… (1).c4z`). Its first uibutton proxy (the status tile, listed first in its driver.xml, so it gets the lowest id) is a device of the new kind `refrigerator`, with that tile's name and room; the four feature tiles are no devices of their own, and are not listed as other devices. Variables and the event are read on the refrigerator's driver itself and routed to that device, as a DoorBird's events are to its doorbell (`src/adapters/refrigerator.lua`, `src/control4/normalize.lua`).
- **Read through change notifications.** The variables are found by name, else by those ids, and watched (`C4:RegisterVariableListener`), except the power. `GET /v1/refrigerators` and `/{id}` (viewers) give `online`, the fridge's and freezer's temperature and setpoint in °C to 0.1, `door_open`, `water_filter_usage`, the four features on or off, `features` (the ones `PATCH` takes) and `features_reported`; `GET /v1/devices` lists it with type `refrigerator` and that address; `/v1/system` counts `inventory.refrigerators` and says `features.refrigerators`.
- **Unknown support and units, with driver 1.0.0 as it is.** All four features are listed (`features_reported` false): a model without one is refused by its driver, and the app shows the command as not confirmed. An exact 0 is taken as not reported (null): a setpoint is never 0 °C (a fridge's are 1 to 7, a freezer's below −14) and a fridge is hardly ever at exactly 0 °C; a freezer's 0 is believed in °F, where it is a usual setting. A new water filter's 0 % shows as not reported. The unit is told by the fridge setpoint (Samsung's are 1 to 7 °C and 33 to 46 °F; 25 and above is °F), else the freezer's (−23 to −15 °C, −8 to 5 °F), else the project's temperature scale.
- **Two variables proposed for the refrigerator driver** (a local branch `dev/directorlink-vars` of its repository, not published): `REPORTED_VARIABLES`, the variables that hold a value this refrigerator reports, and `TEMPERATURE_UNIT` (`C` or `F`), both added after the twelve, so no id moves, and empty until the first read. When they are there, DirectorLink takes them at their word: only the features the model has, null for what it lacks, the unit as said. Without them, or while empty, the rules above.
- **Switched like other slow devices.** `PATCH /v1/refrigerators/{id}` with any of `power_cool`, `power_freeze`, `sabbath_mode`, `ice_maker` (members and up; `409 FEATURE_NOT_SUPPORTED` for one the model does not have, before anything is sent) sends `SET_FEATURE {Feature, State = On | Off}` to the refrigerator's driver and answers `202` with the state last reported. The app moves the switch at once, says "Turning on…", reads the refrigerator every 2 s, and holds the switch once it reports the change; after 65 s (the driver reads the refrigerator again about 3, 10, 25 and 55 s after a command) it puts back what the refrigerator reports and says it did not confirm, then keeps reading it quietly every 5 s for 2 minutes, and shows the change, without that word, if it comes (the driver may see it at its next poll).
- **Scenes and schedules.** A step of type `refrigerators` sets any of the four features on or off, on the refrigerators it names or all in a room or the home. A feature a refrigerator does not have is left out on it (`partial`, or skipped with `NOT_SUPPORTED`). It needs no more than a member, so schedules run it: a Shabbat schedule switches Sabbath Mode. The app's Add an action offers Refrigerators: which, which feature (the ones they have), on or off. Copy the house leaves refrigerators out. Backups carry the steps and favorites, matched to the project like any device.
- **Kept through a downgrade.** DirectorLink 1.6.0 does not know the step: it leaves it out when it loads the scenes (the other steps run) and its next save of any scene drops it. So the steps are also kept under `directorlink_scene_steps`, which 1.6.0 does not read, and 1.7.0 puts them back in their places in a scene that comes back without them. Only after a save by an older version: the scenes record 1.7.0 writes has `steps_kept`, a field 1.6.0 drops when it saves, and steps are put back only when it is missing, so a step removed in 1.7.0 stays removed even if the copy could not be written then (logged).
- **A door left open.** The driver's Door Left Open goes into the history as a door entry (`left_open`, by DirectorLink), once per opening (the door must close in between), and runs one hook in `main.lua`, `Refrigerator.onDoorLeftOpen(device, seconds)`, which also sends the push alert of ADR-050 (`Alerts.fridgeDoor`) to the members and admins who chose it; a home with a refrigerator offers them that choice. `seconds`: since DOOR_OPEN turned "1" (kept through a project refresh), so the door has been open at least that long; the alert says the whole minutes ("for at least 6 min"). A door already open when DirectorLink started has no time, and the alert says only that it was left open.

**Why:** The owner's driver already does the hard part (the cloud, its sign-in, confirming each command), so DirectorLink reads what it publishes rather than talking to Samsung itself, which would need a second sign-in and would put a cloud on DirectorLink's Lua thread. One device rather than five tiles, because the family thinks of one refrigerator. °C in the API, because every temperature in it is (the thermostats'). Working with 1.0.0 as it is, because it is the driver installed; the two variables only remove guesses, and nothing depends on them. The driver's own Door Left Open, because it knows the door's history across its polls and fires once; timing DOOR_OPEN in DirectorLink would be no finer, as the door is read every 2 minutes anyway.

**Consequence:** With driver 1.0.0, a refrigerator without a feature still shows its switch (it does not confirm), a one-door model's missing freezer shows as not reported only because its values are 0, a new water filter shows no usage until it is used, and the door of a model without a door sensor reads closed. A door left open is noticed 6 to 8 minutes after it opened with the driver's defaults (seen at the next poll, then the alert time from that read), and a door opened and closed between two polls is never seen; an installer who sets Door Open Alert to 0 gets no entry and no alert. A restart of the refrigerator driver while a door stays open can say it again. A command takes seconds and needs Samsung's cloud; the app says when it did not confirm. Going back to 1.6.0 hides the refrigerators and their steps (kept for 1.7.0 as above); a backup restored while 1.6.0 runs cannot be told from 1.6.0's own save (it writes no mark and leaves the copy alone), so back on 1.7.0 its scenes get the refrigerator steps the controller had before the restore, in scenes with the same id (docs/SCENES.md); an app not yet updated from 1.6.0 shows a refrigerator step with the wrong words (a door's "Open"), and saving that scene in it drops a step that names refrigerators. Not yet seen on a real controller: the ids, names and values of the driver's variables as Director returns them, which proxy is the first, its tiles' names and rooms in `C4:GetDevices`, and the event's delivery to another driver.

## ADR-048 — Automatic backups to the account, sealed to a backup password only the family knows; the Sonos room choices in backups

**Context:** A backup (ADR-042) exists only if an admin remembered to download one and kept the file. A controller that dies, or a driver removed by accident, months after the last download loses everything since. The account service already holds each home's relay connection, so it could keep a backup every night, but it must never be able to read one: a backup holds every key's lock key and the home secret (ADR-042), and the cloud never sees what the home does (docs/ACCOUNTS.md). The controller cannot keep a secret from someone who copies its data, and its crypto is plain Lua on a slow CPU (ADR-039). The token has no R2 access; D1 takes rows up to 2 MB. The Sonos room choices (ADR-044) were left out of backups.

**Decision (1.6.0):**
- **A backup password, held by the family only.** An admin sets it once in the app (Settings → Controller → Backup → Automatic backups to your account; signed in, the home linked), typed twice, at least 10 characters, with the backup file's strength hint; the app says plainly that a lost password means the backups cannot be opened, by anyone. The browser makes an X25519 key pair from it, PBKDF2-SHA-256 with 600,000 iterations and a random 16-byte salt giving the private key's 32 bytes, and sends the controller only the public key, the salt and the iterations (`PUT /v1/backup/automatic`, admins, sealed requests only, so that nobody on the network can swap in their own key; `DELETE` turns it off, sealed too). Changing the password sends a new key; older backups keep theirs, and the account lists each backup with its key's id (the public key's first 8 bytes) so the app can say "earlier password". `GET /v1/backup/automatic` (admins) gives the key's id, the time and the last backup's outcome, and the public key, salt and iterations only in sealed requests (1.6.0 review: in the clear they would let someone on the network test password guesses); `features.automatic_backup` in `GET /v1/system` says the driver has it.
- **Sealed on the controller to that key** (`src/cloud/backup_seal.lua`): the same document as `GET /v1/backup`, sealed with an ephemeral X25519 key used once: the shared value gives a lock key `HMAC-SHA256(shared, "DirectorLink cloud backup v1|" + epk + "|" + public key)`, then the lock's `enc` and `mac` keys, AES-256-CBC with a random IV, and an HMAC-SHA256 over the label, key id, salt, iterations, ephemeral key, IV and ciphertext, through C4:HMAC and C4:Encrypt as every sealed request (ADR-029). AES-GCM is not used: Director's C4:Encrypt is known to do AES-256-CBC (the lock's self-test), not GCM. The ephemeral key is forgotten once sealed, so the controller cannot open its own backups. Test vectors made with Node's crypto (`tests/vectors/cloud_backup.json`) are reproduced by the driver and opened by the app.
- **Never long on the Lua thread.** The X25519 ladder runs 64 of its 255 steps at a time (`X25519.start`, `job.step`); the document, its JSON, each slice, each inversion, the encryption and each chunk run in a timer tick of their own (`src/cloud/auto_backup.lua`). Measured on a PC for a big home (130 KB of JSON): 16 ms for the document, 10 ms for the JSON, about 70 ms of Lua for the seal in 11 steps of at most about 15 ms; the CORE-1's Cortex-A53 is 5 to 10 times slower. `backup uploaded` logs the real `seal_ms`.
- **Every night, and Back up now.** At the home's own minute between 03:00 and 04:59 (the controller's time, picked at random once, so that homes do not all send at once), from the scheduler's minute tick, and on **Back up now** (`POST /v1/backup/automatic/run`, `202`). Only while Remote Access is on, the relay has accepted the home's identity (`linked`) and the lock passed its self-test (`409 REMOTE_ACCESS_OFF`, `HOME_NOT_LINKED`, `AUTOMATIC_BACKUP_OFF`, `BACKUP_RUNNING`; `503 REMOTE_OFFLINE`, `LOCK_UNAVAILABLE`, `PROJECT_NOT_READY`). A daily backup that could not be made is tried again every 15 minutes until 06:00, then that day has none; Remote Access off is logged once a day. One log line each: `backup uploaded` (size, chunks, times: what a history can show) or `automatic backup not made` (why).
- **Over the relay connection, in chunks.** `backup_chunk` messages (docs/RELAY.md) of 60,000 characters, each sent once the one before is answered `backup_result`; the first says the count, the whole size and the key's id. The relay's Durable Object checks each (size, order, the home's own upload, a claimed home: `NOT_CLAIMED` otherwise) and writes it to D1 (`cloud/src/backups.js`, `migrations/0007_cloud_backups.sql`): the ciphertext in chunks well under D1's 2 MB a row, its size, when it came and the key's id. Nothing about the home.
- **What the account keeps.** One backup a day per home (UTC; a newer one the same day replaces it, and does not count against the others), the last 7, at most 5 MB a home: above that the oldest go first and the newest always stays. The homes of one owner hold at most 25 MB together: above that the oldest go first across them, each home's newest stays, and a backup that would not fit beside the newest of the owner's other homes is refused (`ACCOUNT_BACKUPS_FULL`). One backup is at most 3,000,000 bytes (the largest a driver makes, 2 MiB of JSON, is about 2.8 MB sealed; a big home's is about 175 KB); a larger one is not sent (`BACKUP_TOO_LARGE`: download a file instead). The account takes only printable ASCII (the sealed text is JSON around base64), so characters are bytes. A home starts at most 4 backups a UTC day, and its first nightly one (`"why":"daily"` on the first chunk) besides (`BACKUP_LIMIT`). They go when an admin deletes them (`DELETE /v1/homes/{home_id}/backups`; turning automatic backups off keeps them), with the home when its owner deletes the account, and an upload that never finished after an hour (daily cron).
- **Who reads them: the home's admins.** `GET /v1/homes/{home_id}/backups` (id, date, size, key id) and `GET …/backups/{id}` (the sealed text). The cloud does not know roles: a 1.6.0 controller's `keys` message says which key ids are admins' (`admins`, ADR-047), and the accounts that use one pass, the home's owner too only then, as for alerts. A controller before 1.6.0 says none: then only the home's owner passes, who claimed the home with an admin key at home. `mayUseBackups` in `backups.js` is the one place that decides.
- **Restoring one** goes through the same check, preview and Replace everything as a file (ADR-042): the app lists the backups of the account's homes it may see, the admin types the backup password, and the browser downloads it, makes the private key again from the password and the backup's own salt and iterations, checks the MAC (a wrong password or a changed backup opens nothing and sends nothing) and hands the document to the controller in sealed parts.
- **The Sonos room choices go into every backup** (manual and automatic) as the section `sonos_rooms`, its store as kept, and come back with a restore: each player's room matched to the project like a scene's room (by id and name, else by name; a room that is gone is left out and listed with the player that used it), written with the other stores, all or none. A backup made before 1.6.0 has no such section: it restores as before, and the choices on the controller stay. A Sonos store that could not be read at start stops only a restore that has the section (`503 UNAVAILABLE`).

**Why:** A backup made every night without anyone remembering is what saves a family whose controller died. The password in the browser and only its public key on the controller, because neither the cloud nor a copy of the controller's data may open the backups, and the controller must be able to seal without anything to unlock first; X25519 sealing because it needs nothing but the public key, and an ephemeral key because then not even the controller can open what it sent. CBC and HMAC through Director, because they are what Director is known to do and the browser opens them with WebCrypto. Slices on timers, because the CORE-1 does a scalar multiplication in 0.15 to 0.3 s and Director runs everything else on the same thread. D1, because R2 is not available, in chunks because of D1's row size, and one a day for seven days within 5 MB, because that keeps a week's history, bounds what a home costs, and stops pressing Back up now from pushing out last week. Starts a day and 25 MB an owner, because D1 is shared by every account and anyone can run a driver and claim homes: a home without them could rewrite 3 MB at will, and an account could fill the database with as many homes as it claims. Pruning the oldest across the owner's homes rather than refusing, because a refusal would keep old backups and lose the newest, which is the one a family needs. The controller's admins, the owner included only with an admin key, because the cloud must not guess roles, and a viewer's account must not get a backup (even sealed). The Sonos choices, because a restore should bring the home back as it was.

**Consequence:** A lost backup password cannot be recovered: those backups are lost (the app says so when it is set). Whoever has a backup and its password has the home's keys (ADR-042): the password should be one the family keeps apart. The account service sees each home's backup size and time, which say little. With a controller before 1.6.0, which announces no admin roles, admins who are not the home's owner cannot list or restore the account's backups (they can still download a file); with 1.6.0 an owner whose keys are no longer admins' cannot either, and an owner whose key the account has not seen yet (no sealed request through the account) is refused until the app has made one. A fifth Back up now in a UTC day fails with `BACKUP_LIMIT`; the nightly backup still goes. After a controller is replaced, an admin pairs one device at home, signs in, restores from the list (the identity moves by ADR-042's rules: tick Move remote access), and sets the backup password again: a new controller has no key. A downgrade to 1.5.0 ignores the backup password's key (it stays stored) and a 1.6.0 backup is refused there as too new (ADR-042). Migration `0007` must be applied before the Worker that uses it is deployed. Not yet seen on a real controller: the times of the slices on a CORE-1 (the log says), and `backup_chunk` frames of 60 KB through Director's TLS connection.

## ADR-047 — Alerts: Web Push to the home's admins when the home is offline or a schedule failed

**Context:** The app could notify only while it was open (doorbell rings). The owner wants to know on his phone and computer, with the app closed, when the home has been unreachable for a while or a schedule did not do its job, and nothing else: no "back online", no "backup failed". The cloud does not know what the home does, its name, or who is an admin there (ADR-029): only which account uses which key id (`member_keys`).

**Decision (1.6.0):**
- **Two alerts, to admins only.** *Offline*: the home has been away from the relay for 10 minutes, once per absence. *Schedule failed*: a scheduled scene ran and a device refused, or it could not run; at most three an hour. The words are generic, as the cloud knows no names: "Your home – a schedule had a problem at 08:00. Open the app to see what happened." Tapping one opens Settings → Controller → History.
- **Standard Web Push, encrypted.** The Worker signs each push with a VAPID key (RFC 8292, ES256; the private key is the secret `VAPID_PRIVATE_KEY`, a JWK that `scripts/vapid_key.mjs` makes and pipes into `wrangler secret put` without showing it; the public key is the var `VAPID_PUBLIC_KEY`) and encrypts the message for the browser (RFC 8291, aes128gcm) with WebCrypto, tested against the RFC's vector. The message is `{kind, home, at}` and nothing else. The service worker shows it with the app's own words, which the app keeps for it in Cache Storage in its language, and the time on the device's clock (the cloud does not know the home's time zone). An unreadable push shows a generic one: every push shows a notification. Only the push services browsers use are taken as addresses (Google, Mozilla, Apple, Microsoft), never one a user names.
- **Who is an admin.** The controller's `keys` message (docs/RELAY.md) also lists which ids are admin keys (`admins`). An account is an admin of a home while it uses one of them there, checked when a browser registers and again for every alert, so a key made a member or revoked stops its account's alerts at once. A driver before 1.6.0 says nothing, and then nobody can switch alerts on (`409 ROLES_UNKNOWN`).
- **Registering.** Settings → Controller → **Alerts on this device**, for admins signed in to an account, on a device linked to the home: the switch asks for permission (only there), subscribes the browser with the cloud's key and registers it (`POST /v1/homes/{home_id}/alerts`; `DELETE` to stop). D1 keeps, per home and browser, the push address, the browser's public key and secret, the account and when (`push_subscriptions`, migration 0006), at most 10 browsers per account and home. A subscription goes when its account leaves the home, is removed, or is deleted, when another account claims the home, when the account signs out everywhere (or Apple ends its only sign-in), signs out or forgets its key on that device, and when the push service says the browser is gone (404, 410); each tells the home's Durable Object, which stops its alarms once no admin's browser is left (and, connected, asks D1 again every hour). The app registers again at each start, signed in, so a new subscription or a new VAPID key is picked up. Push addresses are only the push services' hosts on HTTPS's own port, and a redirect is never followed.
- **Offline, without false alarms.** Only while an admin's browser is subscribed, the home's Durable Object sets alarms: 10 minutes after the driver disconnects, and every 10 minutes while it is connected, to see that the driver is still heard on its socket (a socket can die without a close: the relay's stale rule from ADR-045, 1.6.0, counts it as away since the driver was last heard). A driver back within the 10 minutes ends the absence, so drops of seconds never alert. A deploy ends every socket without telling the object; the absence then counts from the first alarm that finds no driver, so the minutes after a deploy alert only for a home that really stays away 10 minutes. An offline alert that reached no push service (D1 failed, or the service was unreachable, answered 429 or 5xx) is sent again a minute later to the browsers it missed, 4 sends at most; only then is the absence marked as alerted.
- **Schedule failed** is told by the driver, from the scheduler's run: `{"type":"alert","kind":"schedule_failed","at":"<time>"}`, only while connected (an unreachable home is the offline alert's), with no schedule, scene or device in it.

**Why:** Push is the only way to reach a closed app, and Web Push works in every browser the app supports, on iPhone and iPad from the Home Screen (iOS 16.4 or later), without a native app. Encrypted rather than empty pushes: the worker must show something for every push and tell the two apart with their time, and fetching the details from a service worker woken in the background would need the account's session and the network at that moment. The words come from the app, not the message: whoever could send pushes (the VAPID key and the database) could only choose among DirectorLink's own sentences and a time. The admins as the controller says, because roles are the controller's (ADR-025): the cloud learns only which key ids are admin keys, not names or other roles. Alarms only for homes that someone would be alerted about, because each one costs a little.

**Consequence:** A home with a subscribed admin costs up to 144 alarms a day while connected (each a Durable Object request and a row written, about 4,300 of each a month) and 24 D1 reads, plus the few seconds of duration each wake keeps the object in memory: at most about 180 GB-s a day if a wake lasted 10 s, about 7 US cents a month beyond the included amounts. Homes without one cost nothing more. The cloud stores push addresses and the browsers' keys, and learns which key ids are admin keys; the push services see that an alert went to a browser and when, never which alert or what it says (every message is padded to 128 bytes). An alert can arrive up to 10 minutes late after a deploy, and an offline alert up to a minute after its 10 minutes. On iPhone and iPad alerts need the app on the Home Screen; elsewhere the browser's permission. Not done: other alerts, per-alert choices, a "back online" notice, the home's name in the text.

**Amended by ADR-050 (1.7.0):** alerts are no longer the admins' only, nor these two only. What the controller alerts about (a doorbell rang, a door or gate was opened, the refrigerator's door was left open, a schedule failed) it seals to each key that gets it, with names; each key chooses its kinds; browsers register with their device's key id (migration `0008`); every push is padded to 1,024 bytes. 1.7.0 drivers no longer send `{"type":"alert"}`; the cloud still takes it from 1.6.0 drivers. The offline alert stays as decided here, the cloud's and the admins', now with a choice per browser (`offline`).

## ADR-046 — The controller keeps an activity history for admins

**Context:** One Shabbat morning the owner's AC did not turn on. Finding out why took a copy of the controller's data and a comparison of snapshots: a Composer status button had been deleted the day before, and its programming with it. DirectorLink's log holds the last 500 lines in memory, mostly API requests, and is gone after a restart; Last Automation in Composer shows one run. Nothing said what had happened, by whom, and why something did not.

**Decision (1.6.0):**
- The driver keeps a history (`src/core/activity.lua`, docs/HISTORY.md): scenes run (by which key, and how many devices ran, were skipped or failed), Home's Turn off all, schedules run and skipped with the reason (Shabbat or a holiday, paused in Composer, the Jewish calendar off for one that runs only on Shabbat, its weather conditions, no weather data) or failed, late runs caught up after a restart, doors and gates opened (also by a scene), relays held and released, keys paired, added, changed in role, removed, removing themselves or expiring, invitations accepted, all keys revoked in Composer, devices and rooms removed, added, renamed or moved in Composer (by name, also devices DirectorLink cannot control; up to 20 a refresh, then how many more), DirectorLink's own Composer settings changed (Remote Access, Schedules, Jewish Calendar, Door Control, Relay Hold, Alarm Status, Sonos), backups made and restored, the remote connection back after more than a minute away, and DirectorLink updated, started or added. Each entry has the time, who (the key's device and the person it belongs to; a schedule with its time and days; Composer; or DirectorLink), what by the names the controller had then, how it went, and a few ids.
- The code that acts says what happened, in one call next to its log line; the module only keeps it, and a failure in it never reaches that code.
- Kept in the driver's persistent data, so it survives restarts and updates: the newest 450 to 500 entries, none older than 30 days, in ten pages of 50. An entry changes only the newest page, which is written at most every 3 seconds, and at once when the driver stops. Entries are cut to 100 bytes a name, whole characters only.
- `GET /v1/activity` for admins: newest first, by kind, in pages (`before`, `limit` up to 200, `next_before`). Like `GET /v1/logs` it may be read in the clear (scripts, the API console); the app reads it sealed, as every request. Members, doors keys and viewers get `403`.
- The app shows it on its own page, Settings → Controller → History (`#/settings/history`), for admins: by day in the home's time zone, an icon per kind, who and what in one line, what was skipped and why in plain words, chips for the kinds, Load more. The app's alert notifications link there; for anyone else the address opens Settings.
- **Not in backups.** The history stays on the controller that made it, and a restore keeps it and adds an entry.

**Why:** "Who did what, and why didn't it run" is the first question when the home misbehaves, and the owner must be able to answer it from the app, not from the controller's files. Names as they were then, because the question is often about something renamed or deleted since. Skips with their reason, because a schedule that did not run leaves no other trace. Pages written at most every 3 seconds, because the controller's flash and its slow pure-Lua JSON should not pay for every door opened; a crash loses at most those seconds. Admins only, because the history shows who opened which door when. Readable in the clear like the log, which already holds the same facts by id. Not in backups: what this controller did is not what another controller (or this one after a reinstall) did, and an old history restored would mix days that happened elsewhere into the answer to "what happened here"; it also says who came and went, which a backup file carried away from the home should not, and it would make a backup bigger for nothing the home needs back. The restore's own entry says when the history starts to mean the restored home.

**Consequence:** Changes made in Composer while DirectorLink was not running are not listed (the first project read after a start has nothing to compare with). A schedule skipped while paused is listed once a run, also when resuming within its 5 minutes then runs it. Lights, AC and blinds changed one by one are not in the history (the log has them). A key revoked keeps its name in the entries made before.

**Changed before release (2026-10-03, after review):** A schedule skipped while the schedules are paused in Composer is listed once for the pause (at its first run skipped, and again only after the schedules have run), not once a run: with 50 daily schedules, two weeks away wrote some 700 entries and left nothing from before the trip. The pause itself is listed as a Composer setting. Automatic backups to the account (ADR-048) are listed as `cloud_backup`, with a reason from a short documented list (`remote_off`, `account_unreachable`, `not_linked`, `too_large`, `stopped`, `error`) rather than the backup's code; a night's backup that fails is listed once, with `note: retry` when it is tried again that night. docs/HISTORY.md says how long the entries last with many schedules: about 500 ÷ N days with N daily ones.

## ADR-045 — The relay connection checks itself, comes back at once, and says why it dropped

**Context:** On the owner's controller (CORE-1 on OS 3.4.3, then X4 on OS 4.2) the relay connection dropped every 10 to 40 minutes: the driver logged `relay connection closed` with `connection lost` (Director reported the connection offline) and was back 5 s later. Cloudflare's log showed the socket ending without a close frame (1006), with nothing before it on the relay's side; another home dropped the same way minutes later. Requests through the account failed during the gap. The driver opened the connection with `MONITOR_CONNECTION = true` and defined no `OnPoll`; Control4 documents that Director then polls the connection and considers it down when no data comes back, but not how often or how long it waits. Cloudflare documents that deploys, runtime updates and edge restarts end WebSockets, with no frequency.

**Decision (1.5.0):**
- Director's monitoring is off (`MONITOR_CONNECTION = false`). The driver's own checks remain: a `ping` every 25 s, answered by the relay's runtime, and a connection that hears nothing for three pings in a row (about 75 s, counted in pings rather than by the clock) is closed (with a close frame, `1000 no answer`) and made again. TCP keep-alive stays on. `OnPoll` answers a poll with a `ping`, in case Director polls anyway.
- A connection that was up for a minute and is lost is tried again after 1 s; then the backoff (5 s, 10 s, 30 s, 60 s). One lost within a minute of opening goes on with the backoff. Closed by the relay with `4000 replaced` (another controller with this identity): 30 s. With `4001 secret replaced`: 1 s.
- Director's `ONLINE` and `OFFLINE` are about the binding, not one connection, so the driver keeps Director's view: the `OFFLINE` that answers its own `NetDisconnect` does not end the next attempt; a connection given up on that comes up late is closed and gets no upgrade request; data arriving while no connection is being made is dropped.
- Every loss and failed attempt is one line in the relay log, with the reason, the next attempt's number and the wait, and what the connection had been doing (`up_s`, `heard_s`, `ping_s`, `polled_s`); `connected to the relay` says how many attempts it took and how long the home was away. Remote Status keeps the last drop's time and reason.
- The relay: a request that finds no driver up to 30 s after the driver's disconnect, or after the relay restarted under the connection (a deploy records no disconnect), waits up to 8 s for its `hello`, then goes through. Requests sent over a connection that a new one replaces fail at once (`502 HOME_DISCONNECTED`) instead of at their 15 s timeout: the old one may have died without the relay noticing. `driver_disconnected` logs how long the socket was up and how long before the end the driver's last ping was answered; `driver_connected` logs how long the home was away.

**Why:** The driver does not need Director to watch the connection: it pings every 25 s and has its own silence rule, so Director's undocumented window can only add drops. Coming back after a second, and having the relay hold a request for a few seconds, turns a drop that cannot be prevented (Cloudflare restarts, the home's network) into a short delay instead of an error. A request already sent is not sent again: the controller may have carried it out. The log lines, because the cause could not be seen from the controller: the next drop says which side ended it.

**Consequence:** Not yet seen on a real controller: that Director still reports a connection the relay or the network ends as `OFFLINE` with monitoring off (if it does not, the silence rule drops it, about 75 s later), and that the drops stop. If they go on, `heard_s` under 25 s with a 1006 at the relay means the connection was cut between the two (the home's network, the provider or Cloudflare's edge), which DirectorLink cannot prevent; the quick reconnect and the relay's wait then keep it short. Two controllers with one identity now push each other off every 30 seconds rather than every few. Drivers before 1.5.0 also benefit from the relay's wait, within their 5 s reconnect.

**1.6.0 (2026-10-03):** With 1.5.0 on the owner's network the connection still died every 20 to 60 minutes at busy times, and Cloudflare's log and the controller's showed how: silently. Cloudflare saw no close and kept the old socket open in the home's object, which went on sending requests into it; the driver learned only when its next ping, up to 25 s later, was refused at once (`connection lost`, `heard_s` 25, `ping_s` 0), and its new connection then arrived as `replaced`, so what had been sent meanwhile failed (`502`, or `504`). The other drops were cuts both sides saw, some of them Cloudflare's restarts. So:
- The driver pings every 10 s and says so in its `hello` (`"ping_s": 10`). The silence rule stays three pings, now about 30 s. A connection that dies is found at the next ping, within 10 s instead of 25.
- The relay takes a socket on which the driver has not been heard (no ping answered by the runtime, no message) for 2.5 of its intervals as gone: 25 s, or about 62 s for drivers before 1.6.0, which announce nothing and ping every 25 s. Requests are not sent into it; they wait up to 8 s for the driver's next connection, as after a disconnect, and go through on it, or answer `503 HOME_OFFLINE`. Once it has been quiet for 30 s more, the answer is immediate. The status, and so `connected` in the account's list of homes, says offline from when the driver was last heard. `driver_stale` is logged once per socket, with `ping_s`. The interval and that mark are in the socket's attachment, which outlives hibernation; a socket whose pings come through again is used again.
- The runtime answers the pings without waking the object (`setWebSocketAutoResponse`); Cloudflare documents that such answers do not wake a hibernating object, incur no wall-clock time and are not charged, so the shorter interval costs nothing.

Requests sent in the seconds between a silent death and the driver's next ping still fail, now within 10 s rather than 25, and are still never sent again. The stale rule only holds requests when the pings stop for longer: a connection whose sends the driver's side does not refuse, which only the driver's silence rule ends.

## ADR-044 — Sonos: DirectorLink talks to the speakers itself, off by default, only to the players

**Context:** The owner has Sonos speakers (three Sonos Amps) and no Sonos driver in Control4, so Control4 knows nothing about them and DirectorLink cannot reach them through Director as it reaches lights. The Sonos app, Home Assistant and Control4 talk to the speakers on the home network with UPnP: SOAP calls on port 1400 to AVTransport, RenderingControl, ZoneGroupTopology and ContentDirectory. Sonos does not document it. Its documented Control API goes through Sonos's cloud and an account. A driver runs on Director's single Lua thread, and anything that talks to the network from inside the home is a way out of the controller.

**Decision (1.5.0):**
- **Off by default.** A Composer property **Sonos** ships `Off`: DirectorLink then looks for no player and sends nothing to one; `GET /v1/music` answers `{"enabled": false, "status": "off", "items": []}`, commands `409 SONOS_OFF`, and `GET /v1/system` says it (`features.sonos`). Set to On (no restart), it searches with SSDP (a UDP network connection on dynamic binding 6100 to 239.255.255.250:1900, as Snap One's SSDP module does; the replies come to `ReceivedFromNetwork`) and reads one player's zone group state, which lists every room and group. **Sonos Address** (optional) names one player for a network the search cannot reach; **Sonos Players** (read-only) lists what was found, with addresses. Turned off, every timer and request stops and answers still on their way change nothing.
- **Only the players.** Requests go only to home network addresses (RFC 1918) on port 1400 that a player gave (its answer to the search, its `Location` in the zone group state) or the installer typed. An API request names a Sonos room by its id (`RINCON_…`), never an address. Album art is fetched only from the player itself (a path on it, or its own address): art a music service keeps elsewhere is not shown. An answer that redirects (any 3xx, or more than one response to a request) is a failure and its body is never used. A search takes at most 32 addresses, each once, kept until the next search unless a player lists them. One file sends (`src/sonos/client.lua`), with a list of the actions it may send (reading, Play, Pause, Stop, Next, Previous, SetVolume, SetMute, and SetAVTransportURI, RemoveAllTracksFromQueue, AddURIToQueue to start a favorite); `scripts/check_package.py` fails the build if another file talks to the players, if anything but the Sonos module allows an address (whatever the client is called there), if `src/main.lua` uses more of the client than handing it the search's network events (`onData`, `onConnectionStatus`), if an action is added (no grouping, alarms or settings), or if Sonos ships on.
- **Cheap, and never waiting.** Every request is asynchronous with a 4-second timeout, at most 4 on their way and 40 waiting; a group is read one request at a time (transport and track on its coordinator, the station or app only when the track changed, then each room's volume and mute); a read the full queue refuses ("busy") is put off to the next tick and never shows a room as not answering. Answers are read in time in proportion to their size (at most 512 KB, 16 KB a tag), whatever a device on the network sends. A room someone has open in the app (its room screen, or Home for all) is read every 4 seconds for 15 seconds after each `GET /v1/music` (the app asks every 5 while it shows them, so reading stops soon after the app closes), the others every minute; the zone group state every 30 seconds while someone looks, else every 5 minutes; the search again every 5 minutes, and after a player stops answering.
- **Rooms.** A Sonos room (a player Sonos shows; a stereo pair or a home theater is one) is shown in the Control4 room of the same name, case and spaces aside, or one of the room's names in other languages; an admin picks the room for the others (`PUT /v1/music/{id}/room`, kept in the driver's store `directorlink_sonos_rooms`, and the admin's choice wins). Unmatched ones are under No room. Hidden rooms and the room order apply as for devices.
- **Groups as Sonos has them.** Play, pause and skip go to the group's coordinator; volume and mute are each room's own (RenderingControl), as there is no group volume in the four services. Pause on a radio stream, which Sonos refuses (UPnP 701), stops it: after a 701 the group's media is read again, and only a stream is stopped; any other refusal is reported. A favorite that is a stream is set as the transport's address; anything else replaces the group's queue and plays, as the Sonos app's Play now. Favorites without an address (shortcuts, such as Sonos Radio's on the owner's players) are listed as not playable.
- **Roles.** Viewers read (what plays, favorites, album art); members control; admins place rooms. Commands answer once the player has taken them (`200` with the room), or `502 PLAYER_UNREACHABLE`, `409 ACTION_NOT_POSSIBLE` (a UPnP refusal), `503 PLAYER_BUSY`.
- **Scenes.** A `music` step pauses or stops the groups with a room in its room, or every group; it names no devices. Each group is first asked what it does (GetTransportInfo): one already paused or stopped is left as it is (a paused queue keeps its place, a paused Spotify Connect session is not ended). Each group handled counts as ran; the players' answers are not waited for (a refusal is logged). A step with nothing to do is skipped with `device_id` 0 and why: `SONOS_OFF`, `NO_PLAYERS` or `NO_SONOS_ROOM` (no Sonos room in its room).

**Why:** Talking to the speakers is the only way without a Sonos driver in Control4, and the local protocol needs no account and no cloud. Off by default, because it reaches devices beyond Director. A fixed port and only addresses the players or the installer gave, because the controller must never be made to contact a host someone names in a request. Polling tied to what the app shows, because the controller has one Lua thread and the owner's three speakers would otherwise be read around the clock for nobody.

**Consequence:** A Sonos update could change the protocol; the parsers are tested against the owner's real answers (anonymised, `tests/sonos/real/`). The search from a driver has not been seen on a real controller; Sonos Address is the fallback. Spotify Connect and AirPlay show the app's name, and the track only when the speaker reports it. The Sonos room choices are not in backups (ADR-042) yet. Read-only checks ran against the owner's players; controls were tested on fake players (`driver/tests/sonos_fake.lua`, `tests/sonos/fake-sonos.mjs`) and are tested by the owner on his.

## ADR-043 — DirectorLink's settings in the app: three changeable, the rest set in Composer only

**Withdrawn before release (2026-10-02, owner's decision): DirectorLink's settings stay in Composer only.** None of what follows shipped: 1.4.0 has no `/v1/settings` routes and no DirectorLink settings in the app, and every DirectorLink property and action is set in Composer, as in 1.3.0. Kept as history.

**Context:** Every DirectorLink setting is a Composer property, and Composer is a dealer's tool many owners cannot use. Pausing schedules for a holiday away, turning the Jewish calendar on or off, or raising the log level for a bug report should not need an installer. Others must not move away from the installer: Door Control and Relay Hold decide whether the app opens doors and gates or holds them open, Alarm Status whether the alarm is watched, Remote Access whether the home is on the internet, and New Pairing Code, Revoke All API Keys and Reset Remote Identity are what an installer uses when a key or the home's identity cannot be trusted.

**Decision (1.4.0):**
- Admins change **Schedules**, **Jewish Calendar** and **Log Level** in the app (Settings → Controller → DirectorLink settings; `PATCH /v1/settings`, and `PATCH /v1/logs/settings` for the log level), and run **Refresh Project** (`POST /v1/project/refresh`). The app shows the other four properties with their value and "Set in Composer", the read-only properties (Status, Version, API Status, Pairing Status, API Keys, Remote Status, Schedule Status, Last Automation, Calendar Status, Inventory; never the pairing code) as Composer shows them, and what **Print Schedules and Scenes** prints (`GET /v1/settings/printout`, the same lines). `GET /v1/settings` lists each setting with its value, choices, whether the app may change it and where it is set. Members and viewers get `403 FORBIDDEN`; drivers before 1.4.0 answer `404` and the app shows no section. While a change is on its way the controls say they are busy (`aria-disabled`) but keep the keyboard's focus. This amends ADR-037: the Jewish Calendar switch is no longer the installer's alone.
- **One path.** A change in the app sets the property as Composer would (`Properties` and `C4:UpdateProperty`, so Composer shows the new value), then runs the code a change in Composer runs (`propertyChanged` in `src/main.lua`, which `OnPropertyChanged` calls). DirectorLink keeps no copy of its own: Director keeps the properties across restarts and updates. `OnPropertyChanged` acts only on DirectorLink's settings (`Settings.LIST`): the read-only properties, the pairing code among them, are DirectorLink's own, and Director may report each update of them back. For each setting DirectorLink remembers the value it applied last (from the app or from Composer); `OnPropertyChanged` with that value, which is Director reporting back what DirectorLink set, at once or later, once or more, changes nothing, and nothing loops. Any other value is a change in Composer, which wins as usual. A setting already at its value is left alone.
- **When applying fails.** If what a setting does fails (pausing the schedules, working the calendar out again), the property keeps the new value and the answer is `500 SETTING_NOT_APPLIED`, naming it, with the error in the log. The property is what DirectorLink reads (the scheduler asks it every minute) and what Composer shows, so it is the truth to report; putting the old value back would run the same code again for it, which can fail the same way, and Composer and the app would no longer agree on what was asked.
- **Set in Composer only.** `src/core/settings.lua` marks each setting and action for the app or not. `PATCH /v1/settings` refuses Door Control, Relay Hold, Alarm Status and Remote Access for every key, admins included (`403 SET_IN_COMPOSER`), before anything changes; no route runs New Pairing Code, Revoke All API Keys or Reset Remote Identity. `scripts/check_package.py` fails the build if the marks change, if anything in the package writes one of those four properties (in either kind of quotes, or as `Alarm.PROPERTY`), if the refusal goes, or if the API reaches one of those actions, turns remote access on or off (`Relay.start`, `Relay.stop`, the relay module) or watches the alarm (`onPropertyChanged`). There is no Composer switch to turn the app's settings off: the three it changes are the owner's to change, and the installer still sees and overrides them.
- **Who.** Every change, made in the app or in Composer, and every Refresh Project, is logged in the category `settings` whatever the Log Level (`Log.always`): the property, its value, `from` (`app` or `composer`) and, from the app, the key's id and name. Nothing else was added to Composer: no existing property fits it, and like every entry it also goes to Director's log (`C4:DebugLog`); the property itself shows the value. The pairing code never reaches the log: every entry is cleared of the current code, as Composer shows it and as typed, in any field and in the message (`Log.hide`).
- Schedule Status and the printout say "Paused", not "Paused in Composer", since an admin may have paused them. Turning the Jewish calendar off and pausing schedules ask in the app first, saying what stops (and that a time due in the last 5 minutes of a pause runs when the schedules are on again). Members and viewers are told that an admin turns paused schedules back on, not where.

**Why:** The owner decides how the family's automation runs; the installer decides what can open the house and what reaches the internet. One code path, and the property as the only place the value lives, keep Composer showing the truth and a later change there winning, without a second implementation to drift. A check in the build, because loosening the line between the two would be a one-word change. Logged whatever the level, because the log is how the owner finds out which key paused the schedules; and the pairing code kept out of it, because the log goes to every admin and to Director's log, and the code pairs an admin key.

**Consequence:** An admin key can pause every schedule or turn the Shabbat schedules off: the log says which key did it. The Log Level the app sets is Composer's, so an installer may find it changed. The statuses are English, as Composer shows them. Not yet seen on a real controller: whether Director reports the driver's own `C4:UpdateProperty` back to `OnPropertyChanged` (both ways are handled). If Director reported back, late, a value DirectorLink set before the last one, it would be taken for a change in Composer.

## ADR-042 — Backups: everything, locked with a password in the browser, restored all or nothing

**Context:** Updating the driver keeps its data, but removing it from the project (by accident), replacing the controller or rebuilding the project loses everything DirectorLink keeps: Control4 deletes a removed driver's persisted data. Keys, profiles, scenes, schedules and the remote identity then have to be made again by hand, every device paired again and the family invited again.

**Decision (1.4.0):**
- `GET /v1/backup` gives one document with every store the driver keeps, each as it is stored with its version (docs/BACKUP.md): the keys as their hashes and lock keys (never a key), profiles, room names and the room order, scenes, schedules without what they ran, the calendar's settings and the remote identity (home id, secret, waiting replacements), but only one the relay has accepted (`linked`: it is a home in the account service), and none is made for a backup; how the Composer properties are set; the names of the rooms and devices the sections refer to; and which controller made it (`controller_id`, a hash of its MAC address, `C4:GetUniqueMAC`). Not in it: pending invitations, the schedules' runtime, the replay guard, the random pool, the weather and the counters. For admins, and only in sealed requests (at home and through the account; `403 SEALED_REQUEST_REQUIRED` otherwise, as `GET /v1/alarm`), because the lock keys and the home secret let whoever has them act as the home's devices and as the home.
- The app locks the document in the browser before it is saved: PBKDF2-SHA-256 with 600,000 iterations and a random 16-byte salt makes an AES-256-GCM key; a random 12-byte IV; the file's header (the file's version, salt, iterations, IV, home, date, driver version) is the additional data, so a changed header or byte does not open, and only version 1, inside the header and out, is opened. The password is typed twice, at least 10 characters, with a strength hint that rates common words, one word with digits or symbols, sequences, keyboard rows and repeats as weak, and the app says that without it the file cannot be opened. The password never leaves the browser and is never written into the page's HTML; the opened document goes only to this controller, in sealed requests. A file over 4 MB is not read. The panel shows only when `GET /v1/system` says the driver has backups (`features.backup`, always true from 1.4.0); a `404` says to update DirectorLink.
- A restore comes back in parts (`POST /v1/restore/parts`, 48 KiB each, 2 MiB and 100 parts in all; one upload at a time per key and three in all, a fourth replacing the one used longest ago; dropped by a timer 10 minutes after its last use, so a checked backup does not stay in the controller's memory), because a sealed request at home is at most 64 KiB and the account's relay takes 128 KiB of ciphertext: raising either would let anyone on the network make the controller hold more, and change the cloud. `POST /v1/restore` checks it (`dry_run`, the default) and restores it only with `"dry_run": false`, the same upload the admin saw checked. It refuses a document that is not a backup, lacks a section or has one of the wrong shape (`422 BACKUP_INVALID`), or that a newer DirectorLink or a newer store version wrote (`409 BACKUP_TOO_NEW`); older ones are read as an update reads their stores. It refuses while a store could not be read when DirectorLink started (`503 UNAVAILABLE`): writing it could lose what it holds, which comes back at the next start, and a restore that failed could not put it back. It then writes every store, or none: each store's values are taken before, and when one write fails, the stores written so far, and that one, get them back (`500 RESTORE_FAILED`). Names (scenes, profiles, keys, rooms) are cut to what the API takes, 64 characters and 10 languages a room, and preferences the API would refuse are left out.
- **Keys.** The backup's keys come back only onto a controller where no key but the restoring admin's is paired, and that one is not in the backup (it was paired after the backup was made): the driver was removed and added again, or the controller replaced. Every device with its key then keeps working without pairing again; the preview lists them by name and role. Otherwise every key stays exactly as it is now, and the preview says "Keys: kept as they are now": a key revoked, or an admin made a member, since the backup was made never comes back. In the reinstall case the admin may say which of the backup's keys this device had ("This device is …", `replaces_key`; none by default): the restoring key then takes that key's profile and role, and that key is not restored, so the owner's old key is not left as an admin key on no device; a choice that would leave no admin is refused (`409 LAST_ADMIN`). The restoring key otherwise stays exactly as it is now (its role, hash, lock key and expiry), and is added with its current profile when the backup does not have that one; a backup key with the same id and another hash stays out (reported as `conflict`). A backup's key record is checked as the driver makes keys: an id of 8 hex digits, a role (none is not admin), a hash of its algorithm's length, a lock key of 64 hex digits or none, and a hash no other key has; the rest is left out and counted (`left_out`, shown). Keys whose expiry has passed, or that have more than 30 days and an hour left (ADR-040: made while a clock ran ahead), stay out, in the preview's counts too. The limit of 20 keys may be passed by the restoring key (`over_limit`): new keys wait until some are removed. Nobody is locked out mid-restore, and there is always an admin.
- **Rooms and devices.** Scene steps, favorites, hidden rooms, room names and the room order are matched to the project: the same id with the same name, still a room or a device of the kind its use needs (a lights step, a light); else the one other room, or device of that kind in the same room, with the backup's name (the ids were swapped, or it was made again); else the same id with another name (`renamed`). What opens doors and gates (relays, doorbells, and a relays step for a whole room) is never moved: it is kept only on the same id with the same name, and otherwise left out and listed with what that id is now (`now`). The rest is left out and listed with where it was used (`unmatched`), never dropped without a word. A step whose room matches nothing is left out rather than kept without it, which would act on every room.
- **Schedules** start as if saved at the restore: nothing due before runs or is caught up, and a weather rule waits until the weather has turned. What they ran belongs to the controller that ran them, and restoring it (days old) could run a Shabbat scene a second time or not at all.
- **Invitations** are not in a backup, and a restore revokes the pending ones and any claim token: an invitation revoked after the backup was made must not come back, and those made since were for the keys and the home there were. They last a week at most; the admin invites again.
- **Another home's backup.** The preview says whether the backup looks like another home's (`origin`): by the home id when both the backup and this controller have one the relay accepted, else by the controller it was made on; and besides when the home's name differs or most of what it refers to is not in this project. Then the app warns first, naming that home and why, Replace everything asks a confirmation that names it, and its remote identity stays out (`kept`) unless the admin ticks **Move remote access to this controller** (`move_remote`, off by default), which says the other controller must be off or reset first.
- **The remote identity.** The backup holds none: the one in use stays (`none`). The same home id: the identity in use stays, with its secrets, which may be newer than the backup's (`same`). Otherwise, and for another home's only when asked (`restore`): the backup's identity is used, its home id and secret checked as the relay takes them (32 lower-case hex digits, 64 hex digits) and its waiting replacements cut to the three the relay tries, none dated after now; the one in use until then is kept as `previous`. Two seconds after the answer (sent on the connection there is, which may be the one the restore came through) the relay connection is made again with the backup's identity. When the relay accepts it, `previous` goes: the home in the account comes back with its members, whose keys the backup has, and the controller announces the key ids to it; the home it used until then goes offline in the account. When the relay refuses it (401 after the waiting replacements: its secret was replaced after the backup was made; or 400, an identity it does not take), the identity from before comes back, the controller connects with that, and the log and Remote Status say so. With Remote Access off, the same happens when it is turned on. A controller with no identity yet takes the backup's without a `previous`. When the identity moves here from a backup made on another controller (or one that cannot be told), the preview warns that the controller the backup was made on must have Remote Access off, or no DirectorLink: two controllers with one identity push each other off the relay (`old_controller`). The app points a device linked to the other home at the backup's.
- **Composer properties** are never restored, only listed with how they are now: a file must never switch a safety setting on (Door Control, Relay Hold, Alarm Status, Remote Access).

**Why:** Everything, because the owner wants the home back as it was, without pairing or inviting anyone again. The lock keys and the home secret must be in it for that, so the file is only ever encrypted and the document only ever sealed. The password in the browser, because the controller must not keep what opens the file, and AES-GCM with an authenticated header, because a changed file must not open rather than open changed. Parts rather than larger requests, because the limits protect the controller and the cloud. The backup's keys only in the reinstall case, because a controller that kept its keys knows better than an older file who may still come in. "This device is …", because the restoring device always pairs anew after a reinstall, and its owner's old key would otherwise be left as an admin key nobody holds. Doors never moved, because a gate's scene pulsing the main door every morning is worse than a scene step missing and listed. The backup's identity rather than the one in use, because the restored keys are the backup home's members'; keeping the current one would leave the family with keys for a home the controller no longer answers as. Only an identity the relay accepted, and another home's only when asked, because one the relay never saw, or another family's, would replace this home in the account and cut everyone off. The fallback, because a secret replaced since would otherwise leave the home unreachable until someone resets it in Composer.

**Consequence:** A backup file and its password together are as good as the home's keys: kept apart, and the file away from the controller. After a reinstall, pair one device and restore at once, before anyone else pairs or is invited: once another key is paired, the backup's keys are not restored. Devices paired after the backup was made pair again, and people who joined after it leave the home in the account (their keys are not in the backup). A device that opened the app while the controller's data was gone forgot its key (the controller told it the key was unknown) and pairs again: restore before the family opens the app. Someone who holds an old backup and its password holds the keys it had until they are revoked (Revoke All API Keys, Reset Remote Identity). If the relay refuses the backup's identity, the family's devices, whose keys are restored, are members of the backup's home, which the controller no longer answers as: they reach it only at home until they are invited again. A backup made before the relay ever accepted the home's identity brings no remote access back: the owner links the home again. Before a restore that moves the identity, the controller the backup was made on must be off, have Remote Access off, or have DirectorLink removed. A backup made by a newer DirectorLink needs that DirectorLink. Through the account the backup goes as one relay message, so a very large home downloads it at home. One key may pass the key limit. Not yet seen on a real controller: `C4:GetUniqueMAC`; without it, backups name no controller, and the home id and the other signs decide.

## ADR-041 — Sign in with Apple is on; the owner approves invitations accepted with another email; Apple's account notifications

**Context:** Sign in with Apple was built in 0.10.0 and hidden until Apple's keys existed; the owner has now set up the Services ID `io.directorlink.signin`, the key (Key ID `Q3WXX95K83`, Team ID `VA4Q88T4RC`) and the primary App ID `io.directorlink.app`. People who sign in with Apple often hide their email (Hide My Email), so an invitation sent to their Gmail never matched and was refused (`EMAIL_MISMATCH`); ADR-027 had planned owner approval for that. Apple also tells apps, server to server, when someone stops using Sign in with Apple for them, deletes their Apple Account, or turns Hide My Email forwarding off or on.

**Decision (1.3.0):**
- **Apple on, only when it works.** The public ids are Worker vars; the `.p8` key is the secret `APPLE_PRIVATE_KEY`, and Apple sign-in counts as set up only with it. The app shows a provider's button only when the account service says it is set up (`GET /auth/providers`, and `sign_in_providers` in `/v1/me`), so a missing secret never shows a button that fails. A device that never signed in still contacts nothing until someone taps **Sign in** (or opens an invitation link, which needs a sign-in anyway); then it asks which sign-ins exist, shows their buttons and remembers the answer. Apple's button follows Apple's Human Interface Guidelines: black, or white on the dark theme; the Apple logo and *Sign in with Apple* (*Continue with Apple* to add it to an account, one of Apple's titles) in one color and the system font; at least as large as Google's and next to it.
- **Another email: the owner approves.** When the signed-in account's emails do not match the invitation's, the app sends the join with `ask_owner`. The cloud then sends nothing to the home: it records a request (D1 `join_requests`, migration `0005`) with a random 6-digit code and answers `202`. The home's owner, and only the owner, sees it in **People and devices** and approves or refuses it (`GET`/`POST /v1/homes/{home_id}/join-requests`). The invited person's page shows the code and asks every 5 seconds (`GET /v1/join/{home_id}/{invitation_id}`); once approved it seals a new join request with the invitation's secret and the cloud relays it as any other join. A refusal is final for that account and invitation; the invitation's expiry, use or revocation ends its requests; an open request can be withdrawn. At most 5 open requests (waiting or approved) per invitation and 20 waiting per home on invitations that can still be accepted, one per account and invitation: a refused request, or one on an invitation that expired, does not keep the invited person from asking. Apps before 1.3.0, which do not ask, still get `EMAIL_MISMATCH`.
- **Owner only.** The cloud knows who owns a home but not the members' roles: those are the controller's keys. Admins could approve only if the controller vouched for them over its connection (a driver change, and the home online), and nothing short of that stops a viewer's account. The owner is also the only one who sees the home's accounts. An admin who is not the owner can make an invitation for the right address instead.
- **What the owner sees, so as not to approve a stranger:** the name the account gave, which nobody checks (anyone can type any name at Apple or Google); its email, or *hidden by Apple*; how it signs in; how old the account is; when it asked; the invitation — its email and expiry from the cloud, its role and the device that made it from the controller, which also says when the invitation is no longer waiting there (Approve is then off); and the code. Whoever got hold of the link could ask too, under any name. The code is the check: the owner approves only when the person they invited reads out the same code, in person or on a call they trust, and the app asks for that in the confirmation.
- **The join's security stays as it was (docs/ACCOUNTS.md).** Asking needs only the ids, so the invitation's secret stays after `#` and on the device; after the approval the controller still opens the envelope with it and uses the invitation up, so an approved account without the secret gets `BAD_MAC` and nothing else. The new key still travels only sealed, and the cloud keeps no envelope (the controller accepts a sealed request only within 2 minutes, which is why the approved join is sealed anew). The invitation stays bound to its email and works once. Membership and the new key id (`member_keys`) are written as for any join, only while the invitation is still pending and the approval still stands, and the join's answer goes through the home's Durable Object after the key work queued before it, in the controller's order. An account the owner refuses while the home is already making its key gets `REFUSED_BY_OWNER` and never the sealed answer (logged `join_key_withheld`); the key made at home is of no use to anyone, and the owner can remove it in People and devices. Revoking the invitation at home, or the admin key that made it, still refuses the join.
- **Apple's notifications**, at `POST /auth/apple/notifications` (entered in Apple's portal on the primary App ID): the body's `payload` is a JWT checked as an ID token is (Apple's signing keys, RS256, issuer `https://appleid.apple.com`), for the audience Apple uses for these, the primary App ID `io.directorlink.app` (`APPLE_APP_ID`); an ID token, whose audience is the Services ID, is refused. `events` is read as Apple writes it, a JSON string (an object too); its time in seconds (milliseconds too). *consent-revoked* and *account-deleted* (Apple's current name; older documents say *account-delete*, also accepted) remove that Apple sign-in, and an account left without any sign-in loses every session. A notice never removes a home, its members or its keys. *email-disabled* and *email-enabled* only update the stored address when Apple gives one: forwarding itself is not stored, and DirectorLink sends no email. A notice dated before the person last signed in with that Apple ID changes nothing, whichever it is (a late or replayed one: that sign-in gave the address Apple has now), each is safe to receive twice, the body is read up to 16 KiB, and Apple's keys are cached for an hour and fetched again early, for an unknown key id, at most once a minute: tokens that arrive during a fetch share it, and a fetch that fails (an error answer, no keys) keeps the keys the Worker had and still counts as the minute's, so posts to this open endpoint cannot make the Worker ask Apple again and again, nor empty its keys. Each notice is one JSON log line with our account id, never Apple's id for the person or an address; a refused one names the audience it had, a public app id, since whether Apple addresses notices for sign-ins through the Services ID to the App ID can only be seen once it is live.
- **An account whose only sign-in was Apple** is signed out everywhere. After *consent-revoked* it stays as it was, homes, members and invitations included (the family keeps its access), and signing in with the same Apple ID gets the same account back (Apple keeps the same id for the person with DirectorLink's team, and the account still records the Apple ID it began with); that Apple ID cannot be added to another account meanwhile (`taken`), or the account would be out of reach for good. After *account-deleted* nobody can sign in to it again, so it keeps nothing of the person: one that owns no home is deleted, as **Delete account** does (its memberships, its requests, the invitations only it could accept); one that owns a home stays so the home and its family keep working, without the person's name and email, outside other homes and without requests to join them. The owner then takes the home over by claiming it again at home with an admin key, from a new account, which as for any change of owner (ADR-027) removes the old members and invitations, who are then invited again. An account left without a sign-in by *consent-revoked* goes the same way once nobody has signed in to it for 90 days (the daily clean-up): the person who comes back after that starts afresh. An owner who also added Google keeps signing in with it.

**Why:** Hide My Email is common, and refusing it left Apple users no way in but workarounds in Apple's settings. The owner already decides who is in the home; a code compared through another channel is what tells the person invited from someone else holding the link, which the name and the hidden email cannot. Apple asks apps to follow these notifications; deleting a home because of one would cut off a whole family, but keeping the name and email of someone who deleted their Apple Account, for good, serves nobody.

**Consequence:** An invited person with another address can join once the owner approves. The approval is only as good as the owner's check of the code, and, like the email check before it, it is enforced by the account service, not by the controller. The invited page must stay open, or be opened again from the link, to finish. The notification endpoint does nothing until it is entered in Apple's portal; until then an Apple ID that stopped using DirectorLink only stops being able to sign in (Apple refuses it). The Worker reads Apple's signing keys for each new key id, cached. Migration `0005` must be applied before the Worker that uses it is deployed.

## ADR-040 — The API console's own key lasts a day

**Context:** The API console does not seal (ADR-032): it sends its key with `Authorization: Bearer` in every request, in the clear on the home network. It pairs for itself an admin key named "DirectorLink Console", which until 1.3.0 worked until someone revoked it, so a key picked up once on the Wi-Fi stayed good for good.

**Decision (1.3.0):** Keys can expire. `POST /v1/auth/pair` takes an optional `expires_in` (whole seconds, 60 to 2592000, 30 days); the key stops working that long after it is made. Once that time has passed, the key is refused with `401 KEY_EXPIRED` and removed at once (the next request is plainly `UNAUTHORIZED`), with its invitations, as a revoked key is; a key that is not presented goes within a minute (the scheduler's tick looks at the keys, which also updates Composer's count and the cloud's list) and before anything that uses the keys (listing, counting, a sealed request, a join, a change of a key, the driver's start), so an expired admin is never counted as another admin, and its invitations never let anyone join. The key views (`GET /v1/api-keys`, `/v1/api-keys/current`, a new key) show `expires_at`, null for never. The console always asks for 86400 seconds for its own key, binds it into the pairing exchange (ADR-039), shows the time left on its Connection screen and warns there that its key travels unprotected; at the end it asks the controller, and `KEY_EXPIRED` sends it back to pairing with "Your console key expired. Get a new pairing code in Composer (DirectorLink → Actions → New Pairing Code)." The console keeps the key's `expires_at` next to it, so a key refused after that time (the controller removed it already, when the app looked at the keys) gets the same message; the clocks may be 5 minutes apart. A key that lasts longer than a browser timer can wait (24.8 days) is asked about every 6 hours. Once, at the first start of 1.3.0 (the key store's version 4), the keys named "DirectorLink Console" from before get `expires_at` a day after that start. Keys made in the console's Keys tab for scripts do not expire, and nothing new is shown there; the app's People and devices shows "expires in …" for keys that do.

**Why:** A day is long enough to work with the console and short enough that a key read on the network is soon of no use; the console is for debugging (its banner says so), not for everyday use. The console's key only: scripts and integrations run unattended, and the app seals.

**Consequence:** Whoever uses the console pairs again each day, with a new code from Composer. The expiry follows the controller's clock; a console on a computer whose clock is ahead asks early and is told the key still works, then asks again a minute later. The controller's clock decides how long a key lasts: a clock put forward ends every key that expires (they pair again), and one put back would make a key last that much longer, so a key with more than 30 days and an hour left (more than any key gets) was made while the clock ran ahead and is over too; a correction of less than an hour changes nothing. The one-time change goes by the name only, so a key someone named "DirectorLink Console" in the Keys tab before 1.3.0 expires too. Going back to 1.2.x drops `expires_at` at the next save, and the console's key then lasts until revoked again.

## ADR-039 — Pairing never sends the code (CPace)

**Context:** Pairing sent the 8-digit code in the clear, over plain HTTP on the home network. The key exchange of 1.0.0 (ADR-032) kept a listener from reading the new key, but someone who could change traffic could read the code, pair with the controller himself and pose as the controller to the app. Local HTTPS is not possible without certificates the app could check; comparing a number on both sides (the fallback plan) asks the person to read digits in Composer twice.

**Decision (1.3.0):** The app and the API console pair with CPace (draft-irtf-cfrg-cpace-21, cipher suite CPACE-X25519-SHA512), the pairing code as the password, in two requests to `POST /v1/auth/pair` (docs/ACCOUNTS.md; api/openapi.yaml). The controller is the initiator A: it answers the app's nonce with its own and its share; the app answers with its share and a tag. `sid` is the two nonces (the draft's recommendation for a session id from both sides); `CI = lv_cat("DirectorLink pair v2", name, expires_in)` binds what the first request asked for; ADa and ADb are empty; the transcript is initiator-responder. Key confirmation is the draft's section 10.4, HMAC-SHA512 with `SHA-512("CPaceMac" || sid || ISK)`: the controller makes the key only after the app's tag is right, and the app opens the key (sealed as before, with `HMAC-SHA256(ISK, "DirectorLink pair v2")`) only after the controller's tag is. A wrong tag is a wrong code, and each attempt counts as one from its first request until it succeeds, within the existing limits (5 per device a minute, 20 per code, 15 minutes, once); a device whose started attempts reached its 5 gets no plain-code guess either until the minute is over. Low-order shares are refused (libsodium's list and the draft's zero check). The driver does SHA-512, HMAC-SHA512 and Elligator 2 (RFC 9380) in plain Lua 5.1 (`src/core/sha512.lua`, `x25519.lua`): CPace hashes bytes (zeros included), and whether Director's `C4:Hash` offers SHA-512 over such data on every controller cannot be checked without one; the app and the console share `app/js/cpace.js` (copied byte for byte, with `js/lock.js`), with WebCrypto's X25519 (deriveBits with the generator or a share as the "public key"; a BigInt ladder where it is missing) and BigInt for Elligator 2. With a controller that refuses the field `cpace` (DirectorLink before 1.3.0), or one whose lock failed its self-test (it answers `503 LOCK_UNAVAILABLE`, so that the two can be told apart), nothing about the code has been sent: the app and the console warn that it would travel unprotected and say why — DirectorLink should be updated in Composer, or, for the lock, there is nothing to update and the installer should look at DirectorLink's log — and only **Pair anyway** sends it, the old way. The warning belongs to the controller it was about: another address, typed or found, clears it, and Pair anyway pairs only that controller. Scripts keep sending the code and getting the key in the answer.

**Why:** CPace is balanced (both sides know the code), small, has test vectors, and fits a code that lasts 15 minutes and works once: a listener learns nothing, and someone in the middle gets one online guess per exchange, which the controller counts. Pair anyway rather than refusing: a home whose driver is not updated yet can still be paired, knowingly; so can a controller whose lock failed, where refusing would leave no way to pair at all (no update fixes it), and the risk is that of 1.2.x. Pure Lua: 70 ms for the controller's half on this PC against 54 ms for the 1.0.0 exchange, about 0.35–0.7 s on a CORE-1, split over the two requests.

**Consequence:** Checked against the draft's X25519 vectors (generator, shares, K, ISK, the low-order points), RFC 9380's curve25519 map (15 vectors), FIPS 180-4 and RFC 4231, in Lua and in JavaScript (Node and Edge), and Lua against JavaScript on random inputs (`tests/vectors/cpace.json`); `scripts/check_contract.py` pairs with a third implementation in Python. Someone in the middle can still stop pairing or use up a code's attempts, and can take the code when Pair anyway is chosen. The Lua code is not constant time; it runs a few times per pairing, on the home network. An app older than 1.3.0 still pairs with a 1.3.0 driver the old way (the driver keeps it).

## ADR-038 — The alarm's status: read-only, off by default, never for viewers

**Context:** bkwagner's pull request #15 read the security partition proxy (`security.c4i`) on a live Director: its variables 1000–1012 give each partition's state (e.g. `DISARMED_READY`), armed home or away and the type of arming, alarm and its type, the number of open zones, the entry or exit delay and the trouble text; a partition the panel does not use says `IS_ACTIVE = 0`. Arming and disarming (`PARTITION_ARM` / `PARTITION_DISARM`) take the user's alarm code. Whether a home is armed tells whoever learns it when the home is empty.

**Decision (1.2.0):** A Composer property **Alarm Status**, next to Door Control and Relay Hold, ships `Off`. While it is Off, DirectorLink does not watch the partitions, `GET /v1/alarm` answers `200` with `{"enabled": false, "partitions": []}` (as `GET /v1/remote` answers `enabled: false` while Remote Access is off), the app shows nothing, and the partitions stay unsupported devices, as before 1.2.0. Set to On (read at every request; the partitions are watched, or let go, at once, without a restart), members and admins, never viewers (`403 FORBIDDEN`), read each partition the panel uses: its state, whether it is armed and how, alarm and its type, open zones, the delay and trouble; on Home and in Settings → Controller in the app. The partitions go only into sealed answers, at home (`POST /v1/sealed`, the app's way) and through the account: a request with `Authorization: Bearer` gets `403 SEALED_REQUEST_REQUIRED`. The answer is padded with spaces to the size it would have with every partition at its longest, so that its size, sealed, depends only on the partitions there are (their names and rooms) and never on their state; for that the panel's words are cut to 32 bytes (the state and the types of arming and alarm) and 100 (trouble), control characters become spaces, and counts stop at 99999. Their state is never logged, at any level. Read-only everywhere: no route, scene step, schedule or Composer action sends anything to a partition, and `scripts/check_package.py` fails the build if the adapter asks Director for anything but reading and watching variables (or loads a module, or prints), if any packaged Lua names a partition command, if a route under `/v1/alarm` is not a `GET`, or if a scene step type reaches the alarm. `GET /v1/system` says whether it is on (`features.alarm_status`), so the app knows whether to show it. In `/v1/devices` a partition stays a device of type `other`, and the API's inventory does not count it as supported; Composer's Inventory adds "N alarm partitions" while it is On.

**Why:** Off by default and never for viewers, because the state says whether the home is empty. Sealed only, because a plain answer would cross the home network in the clear. Padded, because AES only rounds to 16 bytes: an exit or entry delay made the sealed answer longer, and so could an arming for some names, and the home network and the relay see an envelope's size, every 10 seconds while the app is open. Read-only, because arming and disarming take the user's code, which must not travel with an API key: that needs a stronger design of its own (who may arm, where the code is entered and kept, how a disarm through the account is confirmed).

**Consequence:** Scripts and the API console, which do not seal, cannot read the alarm. Each answer carries about 1 KB of padding per partition. A panel text longer than its cap arrives cut. Arming and disarming stay with the alarm's own keypad and app. The IDs and values were read on the contributor's Director; no DirectorLink build has run against a real alarm yet (the owner's home has none), so the first real partition may show a state or type the app words only as the panel writes it.

## ADR-037 — Shabbat and holiday times, worked out on the controller behind a Composer switch

**Context:** Families who keep Shabbat want the home to follow it: the lights and the hot plate before candle lighting, the boiler not on Shabbat morning, the blinds after havdalah. Composer's scheduler knows no Jewish calendar, and setting the times by hand each week is what such a family cannot do on Shabbat itself. The times depend on the home's location, on the community's custom (how long before sunset candles are lit, how long after it Shabbat ends) and on whether Yom Tov is kept one day (Israel) or two (abroad). DirectorLink already works out sunrise and sunset on the controller (ADR-030).

**Decision (1.2.0):**
- A Composer property **Jewish Calendar** ships Off. While it is Off the driver works nothing out, the app shows none of it, `GET /v1/calendar` answers `enabled: false` with nulls (as `GET /v1/remote` does while Remote Access is off) and setting anything that uses the calendar is `409 JEWISH_CALENDAR_OFF`; `GET /v1/system` says whether it is on (`features.jewish_calendar`). A read-only **Calendar Status** shows what it works out, and Schedule Status, Last Automation and the printout show the Shabbat schedules (ADR-031). The installer keeps the switch; the family's custom (candle lighting 20 minutes before sunset and havdalah 42 after by default, and Israel or abroad, automatic from the location, else the project's country or time zone) is theirs: admins set it in the app, and it is kept on the controller (`PATCH /v1/calendar/settings`, with a `version`).
- Everything is worked out in plain Lua on the controller from the project's latitude and longitude, and nothing goes to the network (`scripts/check_package.py` refuses a calendar file that could): the Hebrew calendar (Dershowitz and Reingold), the holidays, the weekly reading (Orach Chaim 428:4 as pyluach formulates it), sunsets by NOAA's solar calculator and Hebcal's roundings (docs/CALENDAR.md). `sun.lua` moved from the Almanac method to NOAA for every schedule: it gives Hebcal's times to the minute 99.8% of the time, against 78%.
- Shabbat and Yom Tov that follow each other are one holy period. A schedule trigger `{"type": "shabbat", "event": "candle_lighting"|"havdalah", "offset"}` (up to six hours either way) runs once when a period begins or ends; `during_shabbat` (`run`, `skip`, `only`) keeps a time, sun or weather schedule away from holy time, from candle lighting to havdalah, or to it. Holy moments are points in time, never minutes of the day, so offsets cross midnight and a clock change moves nothing.
- While the calendar is off or has no location, no moment counts as holy: Shabbat schedules and `only` are kept but do not run, and `skip` runs as usual. Counting `only` as "run as usual" would run Shabbat-only automation every weekday.
- A Shabbat schedule runs once a period, whatever is changed or restarted (it remembers the period's first day and the event). In the first minute after a start, Shabbat schedules and `only` schedules missed in the last 6 hours run late, oldest first, each once, marked `late`; the owner confirmed the 6 hours. Everything else keeps its 5 minutes. What was due while the schedules were paused, or while the calendar was off or had no location, is never caught up, not even by a later restart: the driver keeps, with what the schedules ran, the moment they could run again (`catch_up_after`). Nor is anything caught up when what they ran could not be read at the start, which could run a Shabbat schedule twice.
- The engine is loaded only when the calendar is on, and a failure in it leaves the calendar without times (Calendar Status says so) while every other schedule runs.

**Why:** Off by default, because most homes do not want it, and the switch belongs to the installer as the door switches do; the minutes and Israel or abroad are the family's custom, which they change in the app like their schedules, and Composer is poor for numbers. On the controller, because the schedules that use the times run there, without the internet, and the location stays at home. The catch-up, because a family keeping Shabbat cannot make up by hand for automation a reboot missed.

**Consequence:**
- A home that never turns it on runs as before, except that sunrise and sunset schedules may move by up to a minute, two in the far north (NOAA).
- The times are as good as the project's location; the app and the docs ask families to check them against their community's calendar. DirectorLink works out times; what to automate on Shabbat, and whether a late run is wanted, is the family's decision.
- Where the sun does not set (above about 66°, around midsummer and midwinter) there are no times: a period that lacks its candle lighting or its havdalah runs no Shabbat trigger, neither at its begin nor at its end (a begin without an end would keep the home in Shabbat mode for weeks), and they wait for the next period that has both; the condition counts its civil days, from 00:00 to 24:00, and from candle lighting or to havdalah when that one happens.
- The automatic Israel uses a box around Israel that also takes in parts of Jordan, Lebanon and Sinai; admins there set abroad.
- After a restart during Shabbat a scene may run up to 6 hours late, logged and labelled.
- Going back to 1.1.x loses Shabbat-trigger schedules at the next save (1.1.x refuses them when it loads) and forgets `during_shabbat`, so `skip` schedules run on Shabbat and `only` schedules run on every day they are set for (an `only` schedule at 08:00 every day runs every morning); the next save in 1.1.x drops `during_shabbat` for good. Switch the `only` schedules off before going back, and set skip and only again after returning to 1.2.x; the settings survive. A 1.1.x app still open shows a Shabbat trigger as a rain rule, and saving it in its editor would make it a heat rule; that lasts until the app reloads, and only with the property On.
- The reference data the tests compare with comes from Hebcal.com (CC BY 4.0, credited in NOTICE); nothing is asked of Hebcal at run time.

## ADR-036 — Door relays are pulse-only by default

**Context:** A door or gate on a KNX Contact/Relay device opens while its relay's contact is closed. The app and scenes only pulse relays (close, then open again after 500 ms, as Control4's Relay Door and Gate Controllers do), but `PATCH /v1/relays/{id}` with `{"state": "closed"}` (0.6.0) holds the contact closed, and so the door open, until someone sends `open`. Any key with door access (`doors` or `admin`, with Door Control on) could send it, at home and through the account, and the API console offered it as its example body.

**Decision (1.1.1):** A new Composer property, **Relay Hold**, next to Door Control, is `Not allowed` by default. Until an installer sets it to `Allowed`, `{"state": "closed"}` answers `409 HOLD_NOT_ALLOWED` and nothing is sent to the device. `{"state": "open"}` (releasing the contact, the safe state) and `POST /v1/relays/{id}/pulse` work as before, and the key's role and Door Control are still checked first (`403`). Like Door Control, the property is read at every request, so a change in Composer applies at once, to requests at home, sealed and through the account alike, and is logged. Scenes stay pulse-only whatever it says. The API description's example body is now `open`, so the console no longer offers the hold. `scripts/check_package.py` fails the build when the check in `relays.lua` is gone or either door switch no longer ships off.

**Consequence:** A script or integration that held relays closed gets `409` after the update until Relay Hold is Allowed. The switch is for the whole driver, not per relay: allowing it for a relay that is not a door lets every door relay be held too. The app, scenes and schedules do not change. A key with door access can still open a door, a pulse at a time, but no longer leave it open.

## ADR-035 — Driver updates: a guided notice first, one-tap install only after a test on a real controller

**Context:** Updating DirectorLink means Composer: download `DirectorLink.c4z` from the release, keep exactly that name, and run Update Driver on the device (ADR-010, ADR-014). Admins learned about a release only by watching GitHub. No documented DriverWorks API installs a `.c4z`. The only known method — the unlock key of `C4:FileSetDir`, writing the package into `C4Z_ROOT` and `UpdateProjectC4i` on `127.0.0.1:5020`, used by some open-source drivers — is undocumented and unproven on OS 3.4.3.

**Decision (1.1.0):** The app shows admins that a newer release is out, with What's new, a download of that release's `DirectorLink.c4z` and the Composer steps. The admin's device asks GitHub's releases API (`releases/latest`) at most every 12 hours; other roles never ask, and a driver whose version is not MAJOR.MINOR.PATCH is never compared. Only the version, the date and links into the project's releases are used, never the text of the release notes. Only immutable releases are offered (GitHub's immutable releases, on for the repository from 1.1.0): once published, their tag and files cannot be replaced. Later, and only after a test with a throwaway driver on the owner's CORE-1 succeeds: installing from the app, for admins only, behind a Composer property **App Updates** (default Not allowed), with packages signed in GitHub and checked by the driver, and only to newer versions. Going back stays in Composer. The minimum OS stays 3.3.0 (ADR-001), so the signature is checked in plain Lua.

**Consequence:** Nothing new runs on the controller. GitHub sees admins' IP addresses about twice a day; the privacy page says so. An admin whose app asked just before a release was published hears of it up to 12 hours later. When GitHub gives no usable answer (a rate limit, no connection), a newer release the app already knows of is still offered, but *Up to date* is said only within 3 days of GitHub's last answer; after that Settings says that the check did not work, and when it last did. A release that is not immutable is never offered; it can still say that the driver is up to date (1.0.0, the latest release when the 1.1.0 app went live, was published mutable). With the repository's immutable-releases setting forgotten, admins get no notice of a newer release rather than one for files that could still change.

**1.5.0:** Settings → Controller has **Check now**, which asks GitHub at once but at most once a minute (the 12 hours then start again from it), and shows the app's own version next to the driver's.

## ADR-034 — The driver checks the relay's certificate against roots it carries

**Context:** Up to 1.0.0 the driver opened the relay connection with `NetPortOptions` `SSL` and no `VERIFY_MODE`, and Control4's documentation says Director then checks nothing. Everything through the relay is sealed end to end (ADR-029), but the handshake carries the home secret, so anyone in the network path could pose as the relay, take the secret and keep the home offline.

**Decision (1.1.0):** The connection asks for `VERIFY_MODE = "peer"`, with `CACERTFILE` set to `certs/directorlink-roots.pem` inside the package: the root certificates of the authorities Cloudflare issues the relay's certificate from (Let's Encrypt, Google Trust Services, SSL.com), taken by name from certifi, with each SHA-256 in the file's header. `scripts/check_package.py` checks the options, and that the certificates OpenSSL would load from the file are exactly these roots, each once with its pinned SHA-256, with no key or other block; `scripts/build.py` packages only this file of `driver/certs/`, and `scripts/check_repo.py` allows this one `.pem` and checks its staged content the same way. Control4 does not document how Director reports a certificate that fails the check, so the driver ends any relay connection attempt that has not opened within 30 s and retries with its usual backoff.

**Consequence:** If Cloudflare moves the relay to an authority that is not in the file, or a root expires (2035–2046), remote access stops until a driver update, so the file is rebuilt from a current CA list first (docs/RELAY.md). Control4 does not document whether Director also checks the host name with `peer`; if not, a certificate one of these authorities issued for another name would pass too. Reaching `Connected` shows neither that nor the check itself, so docs/TESTING.md 0p tests the check once with a package that trusts only a root the relay's chain does not end at (`scripts/build.py --roots-only`), which must never connect.

## ADR-033 — Contributed device families and dual setpoints

**Context:** bkwagner's pull requests #14, #19 and #16 added three device families that DirectorLink listed as unsupported, found on a real installation and read on a live Director: the legacy Light proxy, heat-only Thermostat V2 floor heating whose single setpoint is unused, and the Control4 thermostat proxy with separate heat and cool setpoints. They were rebuilt on 1.0.0 (docs/PROJECT_SPEC.md, *Adapters added in 1.1.0*).

**Decision (1.1.0):**
- **Legacy Light proxy** (`light.c4i`): its own adapter, so the Light V2 path validated on real hardware does not change. State from `1000` and `1001` as on Light V2; `ON`, `OFF` and `SET_LEVEL {LEVEL}` with no ramp time, to the proxy; no KNX exception without a trace from a real device.
- **Heat-setpoint rule:** a Thermostat V2 zone follows its heat setpoint only while it is heat-only, its single setpoint reads 0 in both scales and the heat setpoint does not, checked again on every change. On that path it goes down to 5 °C and takes `SET_SETPOINT_HEAT` in the project's scale. Zones with Cool or Auto never take it.
- **Thermostat proxy scale:** the project's scale is required, never guessed. Setpoints are read and compared in its units (whole °F, tenths of °C) and commands go out in it only, whole degrees in °F; the API stays in °C.
- **Public shape:** every thermostat has `setpoints` (`single` or `dual`), `heat_setpoint`, `cool_setpoint` and `setpoint_deadband` (null on single-setpoint ones). On a dual thermostat `target_temperature` is the setpoint of the current mode (null in auto and off), PATCH and scene steps take `heat_setpoint` and `cool_setpoint`, and a `target_temperature` sets the setpoint of the request's mode, else the current one.
- **Push rule:** one setpoint moves the other when needed to keep the deadband; two sent together must already be that far apart. They are sent in the order that never breaks the deadband in between, judged against the setpoints last sent until the thermostat reports them (at most 10 s), so a request that comes before the report is planned from what the thermostat was just told.
- **Safety, as ADR-017:** a device is controllable only when its state variables exist and its listeners register, and every command of a request is checked by its adapter (`Manager.prepare`) before any is sent, so a refused setpoint does not leave the mode changed.
- Fan speeds: the API lists only its own values, which gain `on` and `circulate`.

**Why:** One rule for PATCH, older clients and scene steps. A 1.0.0 client, or an existing "cool 24" scene, sends only `target_temperature`, and that works in heat and cool; sending both setpoints stays strict.

**Consequence:** The API only gains fields, so 1.0.0 clients keep working; in auto they see no target. Room and whole-home scene steps include the new devices. The IDs, values and command lists were read on a live Director; no DirectorLink command has run on these devices yet. The rebuilt adapters are covered by tests against the fake Director and have not yet run on real hardware (docs/TESTING.md 0p).

**Extended in 1.2.0:** fans (#18) were rebuilt the same way. The Fan proxy (`fan.c4i`) has its own adapter: state from `IS_ON` and `CURRENT_SPEED`, found by name, else by the ids read (1000, 1001); `ON`, `OFF` and `SET_SPEED {SPEED}` with 1–4, to the proxy, and nothing sent for anything else; controllable only when both variables exist and their listeners register. `/v1/fans` shows `on`, `speed` and `speeds`, off is `{"on": false}` rather than speed 0, and fans join room and whole-home scene steps. Every fan is taken to have four speeds: the proxy allows 0 to N (`discrete_levels` in its setup), which DirectorLink does not read yet, so a fan with three shows its top speed as Medium High and is sent 4 for High, and one with five or more shows the speeds above 4 only as on. Read on the contributor's Director; no DirectorLink command has run on a real fan yet. A 1.1.x app still open (or cached) after the update does not know fan steps: it shows one as an action of a door (*Open (short press)*), and saving the scene in its editor, or trying it with **Try it now**, drops the fan steps that name devices (*devices no longer in the project*); room and whole-home fan steps are kept. That lasts until the app reloads, as for the Shabbat trigger (ADR-037).

## ADR-032 — The app's key stays off the home network; security review fixes

**Context:** A public review of the code (issue #43) pointed out that an admin key picked up on the home Wi-Fi (plain HTTP) was enough to claim the home to another account and to use it from anywhere; that pairing codes could be guessed through the relay and one person's wrong guesses locked pairing for everyone; that `localhost` was an allowed origin and the `Host` header was not checked (DNS rebinding); that every secret came from `C4:UUID("RANDOM")` alone; that viewers saw the home's exact location; that any member could register invitation ids with the cloud; and that a copy of the controller's data (home secret and lock keys) was enough to pose as the controller.

**Decision (1.0.0):** The app seals its requests on the home network with the lock of ADR-029 (`GET`/`POST /v1/sealed`) and pairs with an X25519 key exchange whose lock also covers the pairing code and both public keys, so its key is not sent in the clear; `Authorization: Bearer` stays for scripts and the console. Pairing is refused as a sealed or relayed request; five wrong codes lock pairing per client address for 60 s and twenty close the code. The driver accepts only DirectorLink's two sites as origins (no `localhost`, also not in development builds: only the local test bridge, `driver/tests/dev_bridge.lua`, also allows `http://localhost:<port>` and `http://127.0.0.1:<port>`) and only IP addresses and local names as `Host` (`421 MISDIRECTED_REQUEST`). Every secret comes from `src/core/random.lua`, a SHA-256 pool stirred with `C4:UUID`, clocks, `/dev/urandom` when readable and each request; only a hash of it is saved across restarts. Once a controller sealed for a device, the app never sends it the key in the clear again (unsigned refusals cannot make it fall back), and `GET /v1/sealed` no longer gives out the home id (envelopes at home name the home `lan`); a sealed request cannot carry another. The location is shown to admins only, rounded to two decimals. The controller registers its own invitations over the relay socket, and the cloud's member endpoint is kept for the home's owner (drivers before 1.0.0). The home's owner replaces the home secret from the app on the home network: the controller makes it and gives only its hash, the account service accepts it only from the owner, and the relay then accepts only it (the controller cannot replace it alone, or a copy of its data could lock it out). The Composer action **Reset Remote Identity** makes a new home id as a last resort. Accounts can sign out everywhere and expired sessions are purged daily. CI actions are pinned to commits, wrangler to an exact version, and `scripts/check_repo.py` refuses local configuration and secret files.

**Consequence:** Someone who only listens on the home network learns nothing that opens the home. Someone who can change traffic during pairing still could (the code travels with the request); local HTTPS or a code compared on both sides would close that, later. (ADR-039 closes it in 1.3.0: pairing never sends the code; ADR-040: the console's key lasts a day.) Old browsers, old drivers and scripts keep working unsealed. A copy of the controller's data still allows acting as its devices and as the home until **Revoke All API Keys** and the owner's **Replace the remote secret** are used (docs/ACCOUNTS.md, *What the lock does not protect*). A device with no sealed request yet (a key paired before 1.0.0) can still be made to send its key once by someone who changes traffic. The API console does not seal. Envelope sizes remain visible to the cloud.

## ADR-031 — DirectorLink's automation is visible and pausable in Composer

**Context:** Dealers' main objection to homeowner-made automation is that it is invisible: "the AC shuts off at 11:30 and nobody knows why" sends the next technician hunting through Composer programming that is not there.

**Decision (0.15.0):** The DirectorLink device shows its automation in Composer: a **Schedules** property (On / Paused) that pauses every DirectorLink schedule, **Schedule Status** (what is on and what runs next), **Last Automation** (the last scene run, when, why — schedule, weather reading or the device that ran it — and the result), and the action **Print Schedules and Scenes**, which lists everything in the Lua output. This extends the rule of 0.8.0 that Composer shows what an installer needs.

**Consequence:** An installer can find, understand and stop DirectorLink's automation from Composer without the app. DirectorLink still does not read or change Composer programming, so conflicts between the two are found, not prevented.

## ADR-030 — Schedules run on the controller; the weather comes from Open-Meteo

**Context:** Schedules must run without an app open and without the cloud, and the owner chose weather rules for heat, rain and wind, without local sensors for now.

**Decision (0.14.0):** The driver keeps and runs the schedules itself, once a minute, in the controller's local time; sunrise and sunset are computed on the controller. The weather is Open-Meteo's (free, no key, CC BY 4.0), asked by the controller directly every 15 minutes while an enabled schedule needs it (or for an hour after the app shows it), with the project's location rounded to two decimals. Weather rules have hysteresis (2°, 10 km/h, a dry hour) and run at most once a day by default. Scheduled scenes run with a member's rights: doors and gates are never opened by a schedule.

**Consequence:** No DirectorLink server is involved in schedules or the weather; the privacy page says what Open-Meteo sees. A controller without internet still runs time and sun schedules; weather rules then wait, and "only if" follows the schedule's choice (run or skip).

## ADR-029 — Accounts, with remote access locked end to end

**Context:** Remote access has to work for people other than the developer, on iPhones too (which cannot use the home-network connection), without the cloud being able to read what homes do. The owner asked for the end-to-end lock to be part of the design from the start, and for Google sign-in first.

**Decision (2026-09-27):** `docs/ACCOUNTS.md` as proposed, with Google as the only sign-in until the whole flow works end to end; Apple follows. Each device's lock key is derived from its API key; remote requests and answers are sealed with AES-256-CBC and HMAC-SHA256 (2-minute window, one-time ids); the owner claims the home once on the home network; everyone else joins by an invitation whose secret stays after `#` in the link; the cloud stores only accounts, sessions, homes, members and pending invitations. Sign-in is Google's authorization-code flow with PKCE, run by the Worker, so no Google script runs in the app's pages.

**Consequence:** A device that never signs in never contacts the account service. The cloud Worker gains a D1 database (`directorlink`) and the `GOOGLE_CLIENT_SECRET` secret; `directorlink.io/privacy` states what is stored.
