# DirectorLink v1.12.0

**Direct to Director. End-to-end integration. Open source.**

iPhones and iPads reach the controller directly at home, adding a user names them, and pairing codes that vary on every controller.

DirectorLink is an independent project, not affiliated with Control4 or Snap One.

## A direct connection at home, for iPhones and iPads too

Until now iPhones and iPads always reached the home through DirectorLink's servers, even on the home Wi-Fi: Apple's browsers don't let a secure page talk to the controller's plain address. Now the controller can also serve DirectorLink securely (HTTPS) under a name of its own, such as `k3f9….dlhome.cc`, which points to its address inside the home network, with a free certificate from Let's Encrypt. At home every device, iPhone and iPad included, then talks to the controller directly: faster, and without DirectorLink's servers. Away from home nothing changes.

It is never on by itself. The installer allows it in Composer (DirectorLink → **Direct HTTPS** → Allowed; Off is the default), and then the home's owner turns it on in **Settings → Controller → Direct connection at home**, which says what it means first. The controller makes its own key, which never leaves it; DirectorLink's servers only get the certificate for it and keep the name pointed at the controller, and renew it before it ends. The name is listed in public certificate logs, as every certificate's name is; it says nothing about whose home it is. Requests stay sealed with each device's own key, as on the home network today. Turning it off removes the name. A router that blocks names pointing inside the home (DNS rebinding protection) keeps the app on DirectorLink's servers until `dlhome.cc` is allowed in it (ADR-082).

## Adding a user

**Settings → Users → Add a user** asks the user's name and access first, then how they connect: a link for their Google or Apple account (works anywhere), or a pairing code at home. The new user gets that name, so nobody is called "Safari on iPad" any more; after joining, their device says "You joined <home> as <name>". Names stay on the controller: DirectorLink's servers never see them. Settings → Account keeps Add my other device (ADR-083).

## iPhone and iPad join in the Home Screen app

On iPhone and iPad, Safari and the DirectorLink app on the Home Screen keep separate data, and alerts work only in the Home Screen app. An invitation opened in Safari now recommends the Home Screen app first, which joins with **Join with an invitation** (paste the link). A Safari tab that already joined can **Move to the Home Screen app**: the app takes its place, and the Safari copy goes away, so it never counts as an extra device.

## Devices you can tell apart

A device in the Home Screen app is called "DirectorLink app on iPhone" (or iPad, Android, Windows), a browser "Safari on iPad", and any device can be renamed in Settings → Users (members rename their own). A user still named after a device is asked "What's your name?" once. A device not used for 30 days says "Not used since …" (or "Never used") next to Remove.

## Pairing codes on 32-bit controllers

On controllers whose software is 32-bit (older models), every pairing code DirectorLink made was the same, 9496 7295, so anyone on that home's network could pair while a code was open. Codes are now random there too. 64-bit controllers, such as the CORE series, were never affected.

## Installing

- **The cloud first:** a Worker update with one new D1 table (`https_names`) and two new secrets for the certificates. Without them Direct HTTPS says it is unavailable and everything else works.
- **Update DirectorLink in Composer** as usual. The app updates by itself.
- **Going back to 1.11.0:** turn Direct connection at home off first (its name stays pointed at the controller otherwise). Names given to users stay. A backup made by 1.12.0 is refused by 1.11.0, as for any newer backup.

## For developers

- `GET /v1/system`: `direct_https` (`null`, or `{name, port, not_after}`); `features.user_names`. New `GET` and `PUT /v1/https` (the owner turns it on; `409 HTTPS_NOT_ALLOWED`, `409 REMOTE_ACCESS_NEEDED`, `403 OWNER_ONLY`). On port 28443 the same API over TLS, sealed requests only from the app.
- `POST /v1/invitations`: `name` (a new user's name) and `move`; `PATCH /v1/api-keys/{keyId}` lets members rename their own devices; `PATCH /v1/profile`: `name`; History: `system` `direct_https` and `access` `moved`.
- The relay: `https` and `https_certificate` messages, `relay_features` lists `https` (docs/RELAY.md). The Worker runs a small ACME client (DNS-01 on Cloudflare) in each home's Durable Object.
